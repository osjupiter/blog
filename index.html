Zero-Downtime Differential Backup with dm-era + LVM Snapshots

Using the kernel's dirty block tracker to copy only what changed, without stopping the device.

What is dm-era?

dm-era is a device-mapper target in the Linux kernel. Device-mapper is the framework behind LVM, dm-crypt, and other block-level abstractions — it lets you stack virtual block devices on top of physical ones. dm-era is one such layer: it wraps an existing block device and maintains a dirty block map.

All reads and writes pass through to the underlying device unmodified. But internally, dm-era keeps a bitmap (writeset) of which blocks have been written. The checkpoint message closes the current bitmap and starts a fresh one under a new era number — a monotonically increasing counter, typically advanced on a cron. Each block remembers the era it was last written as. You can later ask: "give me all blocks last written in era N or later" — and dm-era returns exactly that list, without scanning the device.

This is the key capability for differential backups: if you record the current era at the time of a full backup, you can later extract exactly the blocks that changed since then.

Why dm-era over LVM thin + thin_delta?

LVM thin provisioning has thin_delta, which can diff two thin snapshots to find changed blocks. But it requires the device to be created as a thin volume from the start. If you have an existing device — a hardware RAID, an appliance-managed volume, a plain partition — you can't retroactively add thin provisioning without migrating all the data.

dm-era is different. It can be placed in front of any existing block device, at any time. All you need is a small metadata volume. The origin device doesn't need to be thin-provisioned, doesn't need to be LVM-managed, and doesn't need any special setup at creation time. (The origin does need some way to take a point-in-time snapshot for consistent reads during backup — LVM snapshots, storage array snapshots, etc. dm-era tells you which blocks to read; the snapshot gives you a frozen copy to read from.)

And since dm-era is a simple linear passthrough (not thin provisioning), there's no thin pool to manage — no pool sizing, no monitoring for pool exhaustion, no risk of the pool running full and freezing your writes. The metadata volume is tiny and fixed-size. I/O passes straight through with no indirection.

The Architecture

dm-era wraps an existing block device (the "origin") and uses a small metadata device to track writes.

              Reads/Writes
                  |
           +------v------+
           |   dm-era    |  ← dirty block map per era
           +--+-------+--+
              |       |
     +--------v--+ +--v----------+
     |  metadata | |   origin    |  ← your existing device
     |  (LVM LV) | | (any block  |     (needs snapshot capability)
     +-----------+ |   device)   |
                   +-------------+

The metadata device needs to be on LVM (or similar) so we can snapshot it for era_dump. The origin can be anything — LVM, hardware RAID, a plain partition — as long as it supports some form of point-in-time snapshot. Both are snapshotted independently during the differential backup, without ever stopping dm-era.

How the Differential Backup Works

The procedure has three phases:

Normal operation

Periodic checkpoints advance the era counter on a cron (e.g., hourly). Writes flow through dm-era normally — it just quietly records which blocks are dirty in each era.

Full backup

Take a full backup of the device however you normally do. At the same time, read the current era number and save it alongside the backup. This is the only bookkeeping required — no era-to-timestamp table, just one integer:

$ BACKUP_ERA=$(dmsetup status eradev | awk '{print $6}')
$ echo "$BACKUP_ERA" > /backup/last_full_era

Differential backup

  1. Snapshot the origin (for consistent reads) and the metadata (for era_dump).
  2. Dump the dirty map from the metadata snapshot with era_dump --logical. This outputs an XML file mapping each block to the era it was last written in.
  3. Filter for blocks with era ≥ BACKUP_ERA and read them from the origin snapshot.

The device stays live throughout — no suspend, no freeze.

Using ≥ (not >) is important: the full backup may happen in the middle of an era, so some writes in that same era occurred after the backup. Including the entire BACKUP_ERA means a few blocks are redundantly copied (they're already in the full backup), but no writes are ever missed. The overlap is bounded by one era's worth of writes — with hourly checkpoints, it's negligible.

No timing coordination needed. Checkpoints run on their own schedule. Backups happen whenever. You never need to stop writes or align a checkpoint to a backup.

Experiment: Full Walkthrough

Everything below was run inside a QEMU VM with two virtio disks: vdc (256MB, for era metadata) and vdd (1GB, for the data volume). The kernel is Linux 6.8.0-rc3 from the device-mapper development tree, with CONFIG_DM_ERA=m and CONFIG_DM_SNAPSHOT=m.

1. Setup: LVM + dm-era

Create two separate volume groups — one for the era metadata, one for the data. This lets us snapshot them independently.

# Metadata VG (vdc)
$ pvcreate /dev/vdc
$ vgcreate metavg /dev/vdc
$ lvcreate -L 32M -n erameta metavg

# Data VG (vdd) — this represents your existing storage
$ pvcreate /dev/vdd
$ vgcreate datavg /dev/vdd
$ lvcreate -L 800M -n data datavg

# Zero the metadata device and create dm-era
$ dd if=/dev/zero of=/dev/metavg/erameta bs=4096 count=1000
$ SECTORS=$(blockdev --getsz /dev/datavg/data)   # 1638400
$ dmsetup create eradev \
    --table "0 $SECTORS era /dev/metavg/erameta /dev/datavg/data 64"

$ dmsetup status eradev
0 1638400 era 8 34/8192 1 -
#                        ^current_era=1

The 64 at the end is the era block size in sectors (64 × 512 = 32KB). Every 32KB region of the device is tracked as a single unit.

2. t0–t2: Initial workload + checkpoints

# t0: Advance era (simulating a cron checkpoint)
$ dmsetup message eradev 0 checkpoint
# era is now 2

# t1: writes A — simulate an existing workload
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=100 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=50 seek=400 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=50 seek=700 oflag=direct
# Wrote blocks 0-99, 400-449, 700-749 (all recorded in era 2)

# t2: Another cron checkpoint
$ dmsetup message eradev 0 checkpoint
# era is now 3

3. t3–t4: More writes, then full backup

# t3: writes B
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=50 oflag=direct
# Wrote blocks 50-59 (recorded in era 3)

# t4: FULL BACKUP — record the current era
$ BACKUP_ERA=$(dmsetup status eradev | awk '{print $6}')
$ echo $BACKUP_ERA
3
# In production: dd/rsync/your-backup-tool the full device here
# Writes A and B are on the device, included in the full backup

4. t5–t10: Post-backup writes + checkpoints

This is the interesting part. Writes C happen after the full backup but before the next checkpoint — they land in the same era (3) as the backup.

# t5: writes C — AFTER full backup, but still era 3!
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=300 oflag=direct
# Wrote blocks 300-309 (recorded in era 3 — NOT in the full backup)

# t6: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=4

# t7: writes D
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=5 seek=0 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=20 seek=200 oflag=direct
# Wrote blocks 0-4, 200-219 (era 4)

# t8: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=5

# t9: writes E
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=5 seek=5 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=500 oflag=direct
# Wrote blocks 5-9, 500-509 (era 5)

# t10: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=6

5. t11: Differential backup (zero downtime)

Now we want a diff since the full backup. The device stays live throughout.

# Step 1: Snapshot the data volume (consistent read)
$ lvcreate -L 100M -s -n datasnap datavg/data

# Step 2: Snapshot the metadata volume (for era_dump)
# Take metadata AFTER data — the metadata may include slightly newer
# eras, which means we err on the side of including more blocks (safe).
$ lvcreate -L 32M -s -n metasnap metavg/erameta
# dm-era is still running — no suspend, no downtime

# Step 3: Dump the era map from the metadata snapshot
# --logical outputs a block-to-era mapping (without it, you get raw bitmaps)
$ era_dump --logical /dev/metavg/metasnap | head -8
<superblock uuid="" block_size="64" nr_blocks="25600" current_era="6">
  <era_array>
    <era block="0" era="4"/>
    <era block="1" era="4"/>
    <era block="2" era="4"/>
    <era block="3" era="4"/>
    <era block="4" era="4"/>
    <era block="5" era="5"/>

Each line tells us: block N was last written in era M. To find blocks dirty since the full backup, we filter for era ≥ BACKUP_ERA (3):

# Step 4: Extract dirty block list
$ python3 -c "
import xml.etree.ElementTree as ET
tree = ET.parse('/tmp/era.xml')   # (from era_dump output)
root = tree.getroot()
backup_era = 3
for e in root.findall('.//era'):
    if int(e.get('era')) >= backup_era:
        print(f'block {e.get(\"block\")} era {e.get(\"era\")}')
"

# Output:
block 0 era 4         # writes D (t7)
block 1 era 4
block 2 era 4
block 3 era 4
block 4 era 4
block 5 era 5         # writes E (t9)
...
block 50 era 3        # writes B (t3) — redundant, already in full backup
...
block 59 era 3
...
block 200 era 4       # writes D (t7)
...
block 300 era 3       # writes C (t5) — NOT in full backup, correctly captured!
...
block 500 era 5       # writes E (t9)
...

# Total: 60 dirty blocks
# Step 5: Read the dirty blocks from the data snapshot
$ python3 -c "
import xml.etree.ElementTree as ET
tree = ET.parse('/tmp/era.xml')
root = tree.getroot()
backup_era = 3
bs = 32768
dirty = sorted(set(int(e.get('block'))
    for e in root.findall('.//era') if int(e.get('era')) >= backup_era))
with open('/dev/datavg/datasnap', 'rb') as src, \
     open('/backup/diff.bin', 'wb') as out:
    for b in dirty:
        src.seek(b * bs)
        out.write(src.read(bs))
print(f'Extracted {len(dirty)} blocks = {len(dirty)*bs//1024} KB')
"
Extracted 60 blocks = 1920 KB

# Step 6: Cleanup
$ lvremove -f datavg/datasnap
$ lvremove -f metavg/metasnap
During this entire procedure, the dm-era device was live. We verified by writing to it between steps — no errors, no pauses.
