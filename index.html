Zero-Downtime Differential Backup with dm-era + LVM Snapshots

Using the kernel's dirty block tracker to copy only what changed, without stopping the device.

The Problem

You have a block device (a database volume, a VM disk, whatever). You take periodic full backups. Between full backups, you want differential backups that capture only the blocks that changed since the last full backup. You need this to work:

  • Without stopping or freezing the device
  • Without scanning the entire device to find changes
  • Without precise timing coordination between backups and change tracking

Why not LVM thin + thin_delta?

LVM thin provisioning has thin_delta, which can diff two thin snapshots to find changed blocks. But it requires the device to be created as a thin volume from the start. If you have an existing device — a hardware RAID, an appliance-managed volume, a plain partition — you can't retroactively add thin provisioning without migrating all the data.

dm-era solves this differently. It's a transparent wrapper that can be placed in front of any existing block device, no matter how it was created. All you need is a small metadata volume. The origin device doesn't need to be thin-provisioned, doesn't need to be LVM-managed, and doesn't need any special setup at creation time.

And since dm-era uses a simple linear mapping (not thin provisioning), there's no thin pool to manage — no pool sizing, no monitoring for pool exhaustion, no risk of the pool running full and freezing your writes. The metadata volume is tiny and fixed-size. The origin passes I/O straight through with no indirection.

The Linux kernel has a little-known device-mapper target called dm-era that does exactly this. It sits transparently in front of a block device and records which blocks were written in each "era" — a monotonically increasing epoch counter advanced by periodic checkpoints.

The Architecture

dm-era wraps an existing block device (the "origin") and uses a small metadata device to track writes. All I/O passes through transparently — zero overhead on reads, minimal bookkeeping on writes.

              Reads/Writes
                  |
           +------v------+
           |   dm-era    |  ← records which blocks are dirty per era
           +--+-------+--+
              |       |
     +--------v--+ +--v----------+
     |  metadata | |   origin    |  ← your existing device
     |  (LVM LV) | |  (LVM LV)  |     (on a separate VG/disk)
     +-----------+ +-------------+
         vdc            vdd

The key insight: metadata and origin are on separate LVM volume groups, each with snapshot capability. This means we can snapshot both independently, without ever stopping dm-era.

Why era ≥, not era >

This is the critical subtlety. At t4 (full backup), the current era is 3. But writes C at t5 happen after the full backup and are also recorded in era 3 — because no checkpoint has occurred between t4 and t5.

era > 3 is UNSAFE. It would return 40 blocks (D + E only), missing the 10 blocks written at t5. Those blocks are not in the full backup either — data loss.
era ≥ 3 is SAFE. It returns 60 blocks (B + C + D + E). The 10 blocks from B (t3) are redundant — they're already in the full backup — but writes C at t5 are correctly captured.

The tradeoff: using ≥ includes some blocks that are already in the full backup. But since era checkpoints run frequently (hourly or more), the overlap window is small and the extra data is negligible.

The key property: checkpoint timing and backup timing don't need to be coordinated. Checkpoints run on their own schedule (cron). Backups happen whenever. As long as you record the current era at full-backup time and use ≥ at diff-backup time, no writes are missed.

The Differential Backup Procedure

Setup (one-time)

# Metadata device (separate VG for independent snapshots)
pvcreate /dev/vdc
vgcreate metavg /dev/vdc
lvcreate -L 32M -n erameta metavg

# Origin device (your existing storage)
pvcreate /dev/vdd
vgcreate datavg /dev/vdd
lvcreate -L 800M -n data datavg

# Create dm-era
SECTORS=$(blockdev --getsz /dev/datavg/data)
dmsetup create eradev \
  --table "0 $SECTORS era /dev/metavg/erameta /dev/datavg/data 64"

# Start periodic checkpoints (e.g., hourly cron)
# */60 * * * * dmsetup message eradev 0 checkpoint

Full backup

# Record the current era
BACKUP_ERA=$(dmsetup status eradev | awk '{print $6}')
echo "$BACKUP_ERA" > /backup/last_full_era

# Take your full backup however you normally do
dd if=/dev/mapper/eradev of=/backup/full.img bs=1M

Differential backup (zero downtime)

# Step 1: Snapshot origin (consistent read)
lvcreate -L 100M -s -n datasnap datavg/data

# Step 2: Snapshot metadata (for era_dump)
lvcreate -L 32M -s -n metasnap metavg/erameta

# Step 3: Dump era map from metadata snapshot
era_dump --logical /dev/metavg/metasnap > /tmp/era.xml

# Step 4: Extract dirty blocks (era >= BACKUP_ERA)
BACKUP_ERA=$(cat /backup/last_full_era)
python3 extract_dirty.py /tmp/era.xml $BACKUP_ERA /dev/datavg/datasnap /backup/diff.bin

# Step 5: Cleanup
lvremove -f datavg/datasnap
lvremove -f metavg/metasnap

Why This Works Without Timing Coordination

The traditional approach to change tracking requires you to "start tracking" at the exact moment of your full backup. Miss the window and you either lose changes or have to rescan.

dm-era is different. It's always tracking, at era granularity. When you decide to take a full backup, you just note the current era. When you want a diff, you ask for all blocks written in that era or later. The eras don't need to line up with your backups.

This means:

  • Checkpoints can run on a fixed cron schedule
  • Backups can happen at arbitrary times
  • The only coordination needed: read one integer (current era) at full backup time
  • Worst case: one era of redundant data in the diff (blocks already in the full backup)
