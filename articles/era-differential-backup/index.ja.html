dm-era + LVM スナップショットで実現する無停止の差分バックアップ

カーネルの dirty block トラッカーを使い、デバイスを止めずに変更されたブロックだけをコピーします。

dm-era とは？

dm-era は Linux カーネルの device-mapper ターゲットの一つです。device-mapper は LVM や dm-crypt などブロックレベルの抽象化を支えるフレームワークで、物理デバイスの上に仮想ブロックデバイスを積み重ねられます。dm-era もそうしたレイヤーの一つで、既存のブロックデバイスをラップし、dirty block map（書き込み済みブロックの地図）を管理します。

読み書きはすべてそのまま下位のデバイスに透過されます。ただし内部では、dm-era がどのブロックに書き込みがあったかをビットマップ（writeset）として記録しています。checkpoint メッセージを送ると現在のビットマップが閉じられ、新しい era 番号のもとで新しいビットマップが始まります。era は単調増加するカウンタで、通常は cron で定期的に進めます。各ブロックは最後に書き込まれた era を覚えているため、後から「era N 以降に書き込まれたブロックをすべて教えて」と問い合わせれば、デバイス全体をスキャンすることなく、その一覧だけが正確に返ってきます。

これこそが差分バックアップの鍵となる機能です。フルバックアップの時点の era を記録しておけば、その後「それ以降に変更されたブロックだけ」を正確に抽出できます。

なぜ LVM thin + thin_delta ではなく dm-era なのか

LVM のシンプロビジョニングには thin_delta があり、2 つの thin スナップショットを比較して変更ブロックを求められます。しかしこれには、デバイスを最初から thin ボリュームとして作成しておく必要があります。既存のデバイス — ハードウェア RAID、アプライアンス管理のボリューム、素のパーティションなど — に対しては、全データを移行しない限り後からシンプロビジョニングを追加することはできません。

dm-era は違います。どんな既存のブロックデバイスの前段にも、いつでも配置できます。必要なのは小さな metadata ボリュームだけです。origin デバイスは thin である必要も、LVM 管理下にある必要もなく、作成時に特別な準備も要りません。（ただし origin 側には、バックアップ中に一貫した読み取りを行うためのポイントインタイムスナップショット手段 — LVM スナップショットやストレージアレイのスナップショットなど — は必要です。dm-era が教えてくれるのはどのブロックを読むべきかで、スナップショットはそれを読み出すための凍結されたコピーを提供します。）

さらに dm-era は単純なリニアなパススルーであり（シンプロビジョニングではないので）、管理すべき thin pool が存在しません。プールのサイズ設計も、プール枯渇の監視も、プールが満杯になって書き込みが凍結するリスクもありません。metadata ボリュームは小さな固定サイズで、I/O は間接参照なしにそのまま通過します。

アーキテクチャ

dm-era は既存のブロックデバイス（「origin」）をラップし、小さな metadata デバイスを使って書き込みを追跡します。

              Reads/Writes
                  |
           +------v------+
           |   dm-era    |  ← dirty block map per era
           +--+-------+--+
              |       |
     +--------v--+ +--v----------+
     |  metadata | |   origin    |  ← your existing device
     |  (LVM LV) | | (any block  |     (needs snapshot capability)
     +-----------+ |   device)   |
                   +-------------+

metadata デバイスは era_dump 用にスナップショットを取れるよう、LVM（または同等の仕組み）の上に置く必要があります。origin は何でもかまいません — LVM、ハードウェア RAID、素のパーティション — 何らかのポイントインタイムスナップショットに対応していれば十分です。差分バックアップの際には両者を独立にスナップショットするだけで、dm-era を止めることは一切ありません。

差分バックアップの仕組み

手順は 3 つのフェーズからなります。

通常運用

cron による定期的な checkpoint（例：毎時）で era カウンタを進めます。書き込みは普段どおり dm-era を通過し、dm-era はどのブロックがどの era で dirty になったかを静かに記録し続けるだけです。

フルバックアップ

普段の方法でデバイスのフルバックアップを取ります。同時に、その時点の era 番号を読み取ってバックアップと一緒に保存します。必要な記録はこれだけです — era とタイムスタンプの対応表などは不要で、整数を 1 つ保存するだけです。

$ BACKUP_ERA=$(dmsetup status eradev | awk '{print $6}')
$ echo "$BACKUP_ERA" > /backup/last_full_era

差分バックアップ

  1. origin（一貫した読み取り用）と metadata（era_dump 用）をそれぞれスナップショットします。
  2. metadata のスナップショットから era_dump --logical で dirty map をダンプします。各ブロックが最後に書き込まれた era を対応付けた XML ファイルが出力されます。
  3. era ≥ BACKUP_ERA のブロックをフィルタし、origin のスナップショットから読み出します。

この間、デバイスはずっと稼働したままです — suspend も freeze もありません。

> ではなく ≥ を使うのが重要なポイントです。フルバックアップは era の途中で実行されることがあるため、同じ era 内の書き込みの一部はバックアップ後に発生している可能性があります。BACKUP_ERA 全体を含めることで、少数のブロックは冗長にコピーされます（すでにフルバックアップに含まれているため）が、書き込みを取りこぼすことは決してありません。重複は最大でも 1 era 分の書き込みに収まり、毎時 checkpoint であれば無視できる量です。

タイミングの調整は不要です。checkpoint は自分のスケジュールで動き、バックアップはいつ実行してもかまいません。書き込みを止める必要も、checkpoint をバックアップに合わせる必要も一切ありません。

可視化

実験：全手順のウォークスルー

以下はすべて QEMU VM 内で実行しました。virtio ディスクは 2 本：vdc（256MB、era metadata 用）と vdd（1GB、データボリューム用）です。カーネルは device-mapper 開発ツリーの Linux 6.8.0-rc3 で、CONFIG_DM_ERA=m と CONFIG_DM_SNAPSHOT=m を有効にしています。

1. セットアップ：LVM + dm-era

ボリュームグループを 2 つに分けて作成します — era metadata 用とデータ用です。こうすることで、それぞれを独立にスナップショットできます。

# Metadata VG (vdc)
$ pvcreate /dev/vdc
$ vgcreate metavg /dev/vdc
$ lvcreate -L 32M -n erameta metavg

# Data VG (vdd) — this represents your existing storage
$ pvcreate /dev/vdd
$ vgcreate datavg /dev/vdd
$ lvcreate -L 800M -n data datavg

# Zero the metadata device and create dm-era
$ dd if=/dev/zero of=/dev/metavg/erameta bs=4096 count=1000
$ SECTORS=$(blockdev --getsz /dev/datavg/data)   # 1638400
$ dmsetup create eradev \
    --table "0 $SECTORS era /dev/metavg/erameta /dev/datavg/data 64"

$ dmsetup status eradev
0 1638400 era 8 34/8192 1 -
#                        ^current_era=1

末尾の 64 はセクタ単位の era block size です（64 × 512 = 32KB）。デバイスの 32KB ごとの領域が 1 つの単位として追跡されます。

2. t0–t2：初期ワークロード + checkpoint

# t0: Advance era (simulating a cron checkpoint)
$ dmsetup message eradev 0 checkpoint
# era is now 2

# t1: writes A — simulate an existing workload
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=100 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=50 seek=400 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=50 seek=700 oflag=direct
# Wrote blocks 0-99, 400-449, 700-749 (all recorded in era 2)

# t2: Another cron checkpoint
$ dmsetup message eradev 0 checkpoint
# era is now 3

3. t3–t4：追加の書き込みとフルバックアップ

# t3: writes B
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=50 oflag=direct
# Wrote blocks 50-59 (recorded in era 3)

# t4: FULL BACKUP — record the current era
$ BACKUP_ERA=$(dmsetup status eradev | awk '{print $6}')
$ echo $BACKUP_ERA
3
# In production: dd/rsync/your-backup-tool the full device here
# Writes A and B are on the device, included in the full backup

4. t5–t10：バックアップ後の書き込み + checkpoint

ここが面白いところです。writes C はフルバックアップの後、次の checkpoint の前に発生します — つまり、バックアップと同じ era（3）に記録されます。

# t5: writes C — AFTER full backup, but still era 3!
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=300 oflag=direct
# Wrote blocks 300-309 (recorded in era 3 — NOT in the full backup)

# t6: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=4

# t7: writes D
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=5 seek=0 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=20 seek=200 oflag=direct
# Wrote blocks 0-4, 200-219 (era 4)

# t8: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=5

# t9: writes E
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=5 seek=5 oflag=direct
$ dd if=/dev/urandom of=/dev/mapper/eradev bs=32768 count=10 seek=500 oflag=direct
# Wrote blocks 5-9, 500-509 (era 5)

# t10: Checkpoint
$ dmsetup message eradev 0 checkpoint   # era=6

5. t11：差分バックアップ（無停止）

いよいよフルバックアップ以降の差分を取ります。この間もデバイスは稼働し続けます。

# Step 1: Snapshot the data volume (consistent read)
$ lvcreate -L 100M -s -n datasnap datavg/data

# Step 2: Snapshot the metadata volume (for era_dump)
# Take metadata AFTER data — the metadata may include slightly newer
# eras, which means we err on the side of including more blocks (safe).
$ lvcreate -L 32M -s -n metasnap metavg/erameta
# dm-era is still running — no suspend, no downtime

# Step 3: Dump the era map from the metadata snapshot
# --logical outputs a block-to-era mapping (without it, you get raw bitmaps)
$ era_dump --logical /dev/metavg/metasnap | head -8
<superblock uuid="" block_size="64" nr_blocks="25600" current_era="6">
  <era_array>
    <era block="0" era="4"/>
    <era block="1" era="4"/>
    <era block="2" era="4"/>
    <era block="3" era="4"/>
    <era block="4" era="4"/>
    <era block="5" era="5"/>

各行は「block N は era M で最後に書き込まれた」ことを表します。フルバックアップ以降に dirty になったブロックを求めるには、era ≥ BACKUP_ERA (3) でフィルタします。

# Step 4: Extract dirty block list
$ python3 -c "
import xml.etree.ElementTree as ET
tree = ET.parse('/tmp/era.xml')   # (from era_dump output)
root = tree.getroot()
backup_era = 3
for e in root.findall('.//era'):
    if int(e.get('era')) >= backup_era:
        print(f'block {e.get(\"block\")} era {e.get(\"era\")}')
"

# Output:
block 0 era 4         # writes D (t7)
block 1 era 4
block 2 era 4
block 3 era 4
block 4 era 4
block 5 era 5         # writes E (t9)
...
block 50 era 3        # writes B (t3) — redundant, already in full backup
...
block 59 era 3
...
block 200 era 4       # writes D (t7)
...
block 300 era 3       # writes C (t5) — NOT in full backup, correctly captured!
...
block 500 era 5       # writes E (t9)
...

# Total: 60 dirty blocks
# Step 5: Read the dirty blocks from the data snapshot
$ python3 -c "
import xml.etree.ElementTree as ET
tree = ET.parse('/tmp/era.xml')
root = tree.getroot()
backup_era = 3
bs = 32768
dirty = sorted(set(int(e.get('block'))
    for e in root.findall('.//era') if int(e.get('era')) >= backup_era))
with open('/dev/datavg/datasnap', 'rb') as src, \
     open('/backup/diff.bin', 'wb') as out:
    for b in dirty:
        src.seek(b * bs)
        out.write(src.read(bs))
print(f'Extracted {len(dirty)} blocks = {len(dirty)*bs//1024} KB')
"
Extracted 60 blocks = 1920 KB

# Step 6: Cleanup
$ lvremove -f datavg/datasnap
$ lvremove -f metavg/metasnap

blocks 50-59（writes B）だけが冗長で、フルバックアップと差分の両方に含まれます。これは BACKUP_ERA 全体を含めることのコストです。同じ era の中でフルバックアップより前に書かれたブロックも少し拾ってしまうためです。実運用では、毎時 checkpoint であればこの重複は最大でも 1 era 分の書き込みに収まり、デバイス全体のサイズに比べれば無視できる量です。

決定的に重要なのは blocks 300-309（writes C）の行です。これらはフルバックアップの後に、しかし同じ era の中で書き込まれました。BACKUP_ERA 以降で差分を取ることで、タイミングの調整を一切せずに正しく捕捉できています。

整合性の検証

最後の仕上げのテストです。フルバックアップの上に差分バックアップを適用し、差分取得時に取ったスナップショットと比較します。バイト単位で一致すれば、書き込みは一切失われていないことになります。

# Reconstruct: copy full backup, apply diff blocks on top
$ cp /backup/full.img /backup/reconstructed.img
$ python3 apply_diff.py /backup/diff.bin /backup/reconstructed.img
Applied 60 blocks from diff to full backup

# Compare against the snapshot taken at diff time
$ md5sum /dev/datavg/datasnap
544fb63b202fb3f0eac9f082b17754ac

$ md5sum /backup/reconstructed.img
544fb63b202fb3f0eac9f082b17754ac
完全一致。フルバックアップ + 差分から、差分スナップショット取得時点のデバイスとバイト単位で同一のコピーが復元できました。書き込みの取りこぼしもデータ破損もありません。

まとめ

dm-era はシンプルながら十分に活用されていないカーネル機能で、任意のブロックデバイスに対する差分バックアップを可能にします — シンプロビジョニングも、プール管理も、デバイスの停止も不要です。フルバックアップの時点で整数を 1 つ（その時点の era）記録しておくだけで、次回どのセクタをコピーすべきかを正確に示す dirty block map が得られます。

本記事では、フルバックアップと 1 回の差分バックアップという構成でこのアプローチを実証しました。同じ仕組みは増分バックアップにも自然に拡張できます。バックアップのたびに era を記録し、次回はその era 以降に書き込まれたブロックだけを問い合わせればよいのです。複数の増分チェーン、ローテーション方式、保持ポリシーもすべて実現可能で、era カウンタはただ進み続けるだけです。

今回のテストは小さな VM と合成的な書き込みで行いました。本番のワークロードでは、より大きなデバイス、より高い I/O レート、より長い era の履歴が関わってきます。era block size（今回のテストでは 32KB）は追跡の粒度と metadata のサイズに影響するため、ワークロードに合わせたチューニングを検討する価値があります。他のバックアップ戦略と同様、実際に頼る前にリストア経路をエンドツーエンドで検証してください。

Linux 6.8.0-rc3（dm-6.8 ブランチ）、QEMU VM 上で LVM スナップショットを使用して検証。 era block size：64 セクタ（32KB）。origin：800MB。metadata：32MB。
