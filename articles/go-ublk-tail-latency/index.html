A ublk Loopback Device in Pure Go: GC Tuning and a Comparison with Rust’s rublk

Building a userspace block device without cgo, then chasing tail latency down through the Go runtime: pprof finds two bottlenecks, going async lifts the ceiling 12x, sync.Pool erases the GC tail, and RawSyscall refunds the runtime's fixed costs to match Rust's rublk.

Linux has ublk (kernel 6.0+), a framework for implementing block devices in userspace. Unlike NBD it does not go through a network path: the server talks to the kernel directly over io_uring uring_cmd, which keeps the overhead of the userspace detour small.

This article builds one in pure Go, no cgo: a file-backed loopback device (a homemade /dev/loop0) that appears as /dev/ublkbN. Then, measuring tail latency (p90 / p99 / p99.9) with fio at every step:

  1. Write the obvious first implementation, and watch the GC wreck the tail latency.
  2. Find the causes with pprof and GODEBUG=gctrace=1, then fix them one change at a time: async IO, sync.Pool, fixed buffers.
  3. Compare against rublk, the official Rust implementation from the ublk maintainers, on throughput, tail latency, and CPU.
  4. Break the CPU gap that still remains down thread by thread, identify the Go runtime's sysmon, and stop its interference with RawSyscall.

Everything below is measured. All experiments ran in a disposable QEMU/KVM VM (Ubuntu 24.04, kernel 6.8); the full code lives in the goblk repository.

How ublk works

Three characters appear on stage:

  • /dev/ublk-control: the control character device. Device add, delete, and start commands go here.
  • /dev/ublkcN: a per-device character device. The data plane (IO request hand-off) lives here.
  • /dev/ublkbN: the resulting block device. This is what you mkfs and point fio at.

The interesting part is that both control and data go through io_uring's IORING_OP_URING_CMD. Instead of synchronous ioctls, you embed a command struct inside an SQE (submission queue entry), submit it asynchronously, and receive the result as a CQE (completion queue entry).

sequenceDiagram
    participant App as IO request (app)
    participant K as kernel (blk-mq / ublk_drv)
    participant S as ublk server
    participant B as backend (backing file)
    S->>K: post FETCH_REQ (tag=0..63) up front
    App->>K: read(2)
    K-->>S: CQE (tag=k), desc[k] holds op/sector/len
    S->>B: pread (read the backing file)
    B-->>S: data
    S->>K: COMMIT_AND_FETCH_REQ (result)
    K-->>App: IO completes

You post FETCH_REQ for every tag up front (queue depth 64 here), then loop: receive a CQE, handle it, post COMMIT_AND_FETCH_REQ. One round trip per IO. The request descriptor (ublksrv_io_desc, 24 bytes: opcode, start sector, length) is read not via a syscall but through shared memory mmapped from /dev/ublkcN.

io_uring without cgo

Several Go io_uring libraries exist, but ublk only needs SQE128 (128-byte SQEs, to make room for the embedded command) and uring_cmd, so I wrote a minimal implementation on the standard library's syscall package alone. Zero dependencies. Three jobs:

1. Create the ring. Call io_uring_setup(2) (syscall 425 on x86_64) and mmap the returned fd: three regions, the SQ (submission queue) ring, the CQ (completion queue) ring, and the SQE array (recent kernels merge SQ/CQ into a single mmap).

2. Post SQEs. Write into slot tail & mask of the SQE array and advance the tail atomically. With SQE128 each entry is 128 bytes, and the 80 bytes from offset 48 are the cmd area where ublk's command structs (32 bytes for control, 16 for IO) are embedded directly.

type SQE struct {
	Opcode      uint8
	Flags       uint8
	Ioprio      uint16
	FD          int32
	Off         uint64 // for uring_cmd this is cmd_op (u32)
	Addr        uint64
	Len         uint32
	OpFlags     uint32
	UserData    uint64
	BufIG       uint16
	Personality uint16
	SpliceFDIn  int32
	Cmd         [80]byte // SQE128: offsets 48..127 are the command area
}

3. Submit and wait. io_uring_enter(2) (426) with IORING_ENTER_GETEVENTS blocks until completions arrive. Consuming the CQ is just reading 16-byte CQEs while head != tail and advancing the head.

The ring head/tail words are shared with the kernel, so they are accessed through sync/atomic (matching liburing's acquire/release barriers). Roughly 300 lines total. An "io_uring library" is small if you only build what you need.

Implementing the ublk protocol

Control plane

Device creation is this sequence, all as uring_cmd on /dev/ublk-control:

  1. GET_FEATURES: check kernel support flags
  2. ADD_DEV: pass ublksrv_ctrl_dev_info (queue count, depth, max IO size). dev_id = 0xFFFFFFFF means auto-assign.
  3. Open /dev/ublkcN, mmap the descriptor area
  4. Each queue posts FETCH_REQ for all its tags
  5. SET_PARAMS: device size, logical block size, and so on
  6. START_DEV: /dev/ublkbN appears here

Since kernel 6.4 the opcodes are ioctl-encoded; ADD_DEV is _IOWR('u', 0x04, struct ublksrv_ctrl_cmd) = 0xC0207504.

Queues bind to OS threads

There is one ublk-specific constraint: all IO commands for a queue must come from the OS thread that issued the first one (the kernel binds the queue to that task and verifies it). Goroutines migrate between OS threads freely, so without care you get EINVAL; the goroutine that owns a queue has to call runtime.LockOSThread first to pin its thread:

func (q *queue) run(ready chan<- error) {
	runtime.LockOSThread() // ublk binds the queue to the first submitting task
	...
}

The loopback data path, naive version first

The backend is a file, opened once at startup with a plain open(2) and O_DIRECT; after that everything is fd-based. ublk offers several data-transfer modes; the naive version uses user-copy mode (UBLK_F_USER_COPY, kernel 6.4+): no buffer registration, the server moves data itself by preading/pwriting /dev/ublkcN at a special offset. For every request:

buf := make([]byte, n)                      // allocate every time
switch op {
case OpRead:
	preadFull(backingFD, buf, off)          // read from the backing file
	pwriteFull(cfd, buf, userCopyOff)       // hand to the kernel via ublkcN
case OpWrite:
	preadFull(cfd, buf, userCopyOff)        // collect data from the kernel
	pwriteFull(backingFD, buf, off)         // write to the backing file
case OpFlush:
	syscall.Fdatasync(backingFD)
}

The user-copy pread/pwrite offset encodes queue id and tag as bit fields (0x80000000 + qid<<41 + tag<<25).

"Drop the buffer when done; cleanup is the GC's job." In everyday Go this code is perfectly fine. On a block device data path? Let's find out.

Measurement conditions (common to everything below)

  • VM: QEMU/KVM, 8 vCPU / 4 GiB, Ubuntu 24.04 (kernel 6.8.0-136)
  • Backing: LVM thick LVs on an Intel DC S3710 400GB (power-loss-protected enterprise SATA, via a USB bridge) on the host, passed into the VM as raw virtio disks with cache=none / aio=native, served directly as block devices (/dev/vdc, /dev/vdd). The host page cache is never involved. 8 GiB each, fully prefilled.
  • Raw device baseline (from the guest): 4k randread 217µs / 4.3k IOPS at QD1, ~82k IOPS at QD64; 4k randwrite 45.6k IOPS at QD64. PLP keeps write latency stable.
  • Device: 1 queue, depth 64, 512-byte logical blocks (identical for goblk and rublk)
  • Server threads pinned to CPUs 0-1 with taskset; fio on CPUs 2-7
  • fio: --direct=1, libaio, 3 s ramp. Fixed-rate runs last 60 s, saturation runs 20 s. 4k random: saturation at QD64 (matching queue depth), fixed-rate at QD32. 1M sequential at QD1 (later section).
  • Latency comparisons use a fixed offered rate (--rate_iops). At saturation, latency is pinned by Little's law to QD divided by throughput, so comparing response distributions requires offering every configuration the same arrival rate.
  • The offered rate is 40k IOPS: 70-90% of the async configurations' saturation (randread 52-59k, randwrite 45.3k), the high-load side where queueing amplifies implementation differences.

Results first: four stages compared

The server has four stages, each changing exactly one part of the implementation: v1 sync-naive (make per IO, synchronous backing IO), v2 async-naive (backing IO made asynchronous; allocation identical to v1), v3 async-pool (buffers reused via sync.Pool), and v4 prealloc (fixed per-tag buffers, no allocation at all). The primary metric is saturated IOPS: the real SSD backend driven flat-out at QD64. Hitting the same device directly yields about 80k IOPS, so wherever the ublk device falls short of that, the difference is overhead of the server implementation, not the device.

v1: measuring the naive implementation

Saturation throughput (QD64): 4,335 IOPS randread, which matches the raw device at QD1 (4,328 IOPS) almost exactly. With 64 requests queued but served one at a time, the ceiling pins to 1 divided by the 217µs device round trip. Offer it 40k and it drowns: queueing delay pushes p50 to 7.4ms.

sync-naive:  saturation 4.3k IOPS; at an offered 40k, p50=7439µs (queueing)

Profiling with pprof identifies two causes. The first is the GC. The per-IO make([]byte, 4096) keeps the live heap nearly empty (3->3->0 MB) yet triggers a collection every few tens of milliseconds, and the allocation profile points at that one line:

gc 1593 @101.675s 0%: 0.018+0.18+0.002 ms clock, ..., 3->3->0 MB, 4 MB goal, 2 P

$ go tool pprof -top -sample_index=alloc_space bin/goblk allocs.pb.gz
    1.28GB 99.68%  ublk.(*queue).handleUserCopy   ← make([]byte, n)

The second is synchronous serialization: the loop preads/pwrites the backing file and blocks in place, so while one IO reads the file, the other 63 wait. The CPU profile agrees, showing 71% of CPU time in that synchronous pread wait.

$ go tool pprof -top bin/goblk cpu.pb.gz
     4.58s 87.40%  internal/runtime/syscall/linux.Syscall6
     3.73s 71.18%  (cum) ublk.(*FileBackend).ReadAt   ← blocked in synchronous pread

So v1 has two bottlenecks: the GC (allocation) and synchronous serialization (structure). Advancing with both entangled would make their individual effects unmeasurable, so the structure gets fixed first, and only then does the allocation strategy vary.

v2: making the backing IO asynchronous

The structural fix: move backing-file IO onto the same io_uring as the ublk commands, receiving file IO completions as CQEs too, distinguished by the top bit of user_data. Allocation (a make per IO) stays exactly as in v1.

CQE(ublk: request arrives for tag=k)
  → submit READ/WRITE SQE for the backing file (user_data = tag | 1<<63)
  → keep processing other tags            ←← the difference from the sync version
CQE(backing IO done, bit63 set)
  → COMMIT_AND_FETCH_REQ with its result
async-naive:  p50=701µs  p90=1004µs  p99=1516µs  p99.9=2311µs   5719 GCs
saturation: randread 52.5k IOPS

The ceiling rises 12x and the offered 40k is now served (at 76% of saturation, the p50 of 701µs includes queueing time). This settles it: synchronous serialization owned the tail and the ceiling. The GC remains, though; with more IOPS served, garbage is produced faster and the GC count actually grows. Its effect shows in a p99.9 of 2311µs, the outlier among the async configurations, and in an effective randread rate of 39.3k — slightly dropping the offered load. The next step removes it.

v3: sync.Pool

v1 and v2 allocated the buffer holding each IO's data with make([]byte, n) every time and dropped it afterwards. This step stops that: buffers are borrowed from a sync.Pool, returned after use, and reused. The data hand-off also changes here: instead of the server copying the data via pread/pwrite, buffer addresses are registered with the kernel at FETCH/COMMIT and the kernel does the copying (ublk's default transfer scheme). WRITE payloads are already in the buffer when the CQE arrives, READ payloads are collected at COMMIT, and the data path's only syscall left is io_uring_enter.

q.pool = &sync.Pool{New: func() any {
	b := make([]byte, maxIOBytes) // allocate at max IO size, reuse
	return &b
}}
bp := q.pool.Get().(*[]byte)
buf := (*bp)[:n]
defer q.pool.Put(bp)

Two implementation notes, both general sync.Pool practice. First, store *[]byte rather than []byte: Pool entries pass through an interface (any), so a non-pointer value gets its slice header copied to the heap (boxed) on every round trip, and the pool meant to remove allocations allocates instead. The sync.Pool documentation example states that New should return pointer types for exactly this reason. Second, allocate every buffer at the maximum IO size and use only the first n bytes, so all entries carry the same memory cost. Pooling variable-sized buffers lets a small request pin a huge buffer, or hands back one too small for the request (golang/go#23199; the standard library's fmt caps the buffers it returns to its pool for the same reason).

async-pool:  p50=644µs  p90=914µs  p99=1139µs  p99.9=1385µs   5 GCs
saturation: randread 56.7k IOPS

GC count falls from 5719 to 5. p99.9 shrinks by 40%, from 2311µs to 1385µs, and the 40k offered load that v2 was dropping is now served in full. A single GC pause is short, but 40 thousand requests per second pile into the queue while the world is stopped, so the higher the load, the more the GC's damage is amplified. p50 also moves, from 701µs to 644µs, though the transfer-scheme switch made in this step (fewer data-path syscalls) contributes to that; the 40% at the tail is the GC's.

v4: fixed buffers, no allocation at all

The last step removes the dynamic buffer management through sync.Pool as well. Queue depth is fixed at 64 and each tag carries one IO at a time, so the required regions are known up front: one per tag, 64 in total. They are allocated at startup with mmap (outside the Go heap, invisible to the GC scanner) and registered with the kernel as fixed per-tag addresses.

prealloc:  p50=644µs  p90=922µs  p99=1139µs  p99.9=1385µs   0 GCs
saturation: randread 55.9k IOPS

GC hits exactly zero, but both latency and CPU differences from v3 stay within measurement noise — less of a win than hoped. The reason: v3 had already cut the GC to 5 collections per 60 seconds, so there was almost no interference left to remove. The point of this stage is less performance than establishing the zero-allocation data path that the runtime optimization later depends on.

How to capture this

runtime.ReadMemStats stops the world on every call, contaminating the thing you measure. Go 1.16+'s runtime/metrics reads lock-free, so use that; and since allocating in the writer would fake the "zero" of pool/prealloc, format with strconv.Append* into a fixed buffer:

samples := []metrics.Sample{
	{Name: "/gc/heap/allocs:bytes"},              // cumulative allocations
	{Name: "/gc/heap/frees:bytes"},               // cumulative frees
	{Name: "/memory/classes/heap/objects:bytes"}, // live heap
	{Name: "/gc/cycles/total:gc-cycles"},         // GC count
}
for range time.Tick(25 * time.Millisecond) {
	metrics.Read(samples) // no stop-the-world
	buf = strconv.AppendFloat(buf[:0], time.Since(start).Seconds(), 'f', 3, 64)
	for _, s := range samples {
		buf = strconv.AppendUint(append(buf, ','), s.Value.Uint64(), 10)
	}
	f.Write(append(buf, '\n'))
}

goblk enables this with -metrics out.csv. Capture and plot:

$ sudo ./goblk -impl naive -backend loop -file /dev/vdc -metrics /tmp/naive.csv &
$ fio --rate_iops=40000 ... --runtime=60   # apply load
$ python3 bench/plot_metrics.py            # render PNGs with matplotlib

If you only need GC counts, counting lines of GODEBUG=gctrace=1 gives the same number (cross-checked here). gctrace also carries per-GC pause times and the heap goal, so running both is worth it.

Comparing against the Rust implementation, rublk

The opponent is rublk, the official Rust implementation from ublk-org (the ublk kernel maintainer's org), built on libublk-rs. cargo install rublk, then rublk add loop creates the same kind of loopback device.

To make this a comparison of the languages rather than the setups, the conditions are equalized: 1 queue / depth 64 / 512 KiB max IO / 512-byte logical blocks (all verified identical on both); the backing is the same prefilled 8 GiB S3710 LVs as everything above, with /dev/vdc dedicated to goblk and /dev/vdd to rublk; O_DIRECT on both (rublk defaults to direct_io=1); and all threads are force-pinned to CPUs 0-1 after startup.

saturation (randread):  goblk v4: 55.9k   rublk: 59.3k

40k fixed rate: p50    p90    p99    p99.9   CPU
goblk v4:      644µs  922µs  1139µs 1385µs  39.9%
rublk:         619µs  881µs  1090µs 1319µs  32.3%

The latency distributions are near ties from p50 through p99.9, with rublk a few percent ahead across the range. The clear difference is CPU: goblk burns 1.2x, an extra 7.6 points, for the same 40k IOPS (39.9% vs 32.3%). With zero GCs. Let's chase this difference to the end.

Breaking the difference down by thread

Perf tracepoints and per-thread pidstat break the totals down (the deep-dive numbers in this section come from the preliminary file-backend substrate, but the mechanism applies unchanged to the S3710 substrate):

goblk v3 (total 51.7%):                   rublk (total 39.6%):
  queue loop:      39.5%                    queue thread: 39.6%
  mystery thread:  10.3%                    (that's all)
  misc:            ~2.3%
perf (8s):
  io_uring_enter  52,215                   (rublk: futex and nanosleep ~0)
  futex          169,259   ← 21k/s!
  nanosleep       45,107   ← 5.6k/s

The striking part: the Go thread that actually serves IO costs the same as Rust's (39.5% vs 39.6%). pprof agrees, showing Go user code at measurement-noise level. Per-IO code quality is not where the loss is.

The difference is eaten by two things. First, a thread issuing 5.6 thousand nanosleeps per second: sysmon, the Go runtime's watchdog. It retakes Ps from goroutines blocked in syscalls for over 20µs, and under load it repeats this forever at 20µs-to-hundreds-of-µs intervals (runtime/proc.go; the interval starts at 20µs, doubles when idle, caps at 10ms). Second, 21 thousand futexes per second: the synchronization cost of P hand-off every time the queue goroutine blocks in a syscall. Both are fixed costs the runtime attaches to a "dedicated thread blocking in syscalls" design. rublk has none of this because Rust has no scheduler that needs to take anything from a blocked thread.

Keeping sysmon out of the way: RawSyscall

There is no official switch to stop sysmon. But the source shows it backs off to 10ms on its own when it keeps finding no work (no Ps to retake). So starve it. What tells sysmon about the P is the entersyscall/exitsyscall self-report inside Go's syscall.Syscall6; syscall.RawSyscall6 skips that report entirely.

This is normally forbidden. A goroutine blocking in a raw syscall looks "running" to the runtime, yields its P to nobody, and cannot be preempted; in general code this invites scheduler starvation and delayed stop-the-world. goblk gets away with it because the conditions align: the queue goroutine owns a LockOSThread thread (no one else counts on its P) and the data path allocates nothing, so no GC runs. And because an unbounded invisible block could still stall a stop-the-world while idle, raw waits use IORING_ENTER_EXT_ARG with a 50ms timeout, returning to a safe point at worst every 50ms (the timeout's cost is tens of nanoseconds per wait, under 0.5 CPU points).

This becomes v5. Where v2-v4 changed the implementation structure and allocation, v5 is an independent optimization of the runtime's behavior (its precondition is a data path where the GC effectively never runs, so it applies from v3 onward). The effect of -rawenter:

goblk v4:       644µs  922µs  1139µs 1385µs  39.9%   thousands/s
goblk v5 (raw): 611µs  889µs  1106µs 1352µs  32.9%   ~100/s
rublk:          619µs  881µs  1090µs 1319µs  32.3%   -

sysmon backs off to its 10ms floor (~100/s) and becomes harmless; the futexes collapse to 0.3k/s. The process now has the same shape as rublk (one working thread), its CPU lands at 32.9% next to rublk's 32.3%, and the latency distributions overlap. Refunding the Go runtime's fixed costs brings the server level with the Rust implementation.

sysmon and hand-offs over time

The figure below runs "30s idle → 30s of 40k IOPS → 30s idle" and counts sysmon wakeups (nanosleep) and P hand-off synchronization (futex; hand-offs themselves are not countable from outside the runtime, so the futex syscalls implementing them serve as the proxy) each second.

The normal syscall path (no rawenter) wakes sysmon about four thousand times a second the moment load arrives, futexes at 4-8k/s, then detects all-Ps-idle when load stops and puts sysmon into deep sleep (0/s). rawenter stays a flat line through load and idle alike, nanosleep ≈100/s and futex ≈300/s. The "fixed cost" has become genuinely fixed, and you can see it in the shape of the lines.

Captured with perf's interval mode:

$ sudo perf stat -I 1000 -x, \
    -e syscalls:sys_enter_nanosleep,syscalls:sys_enter_futex \
    -p $(pgrep -o goblk) -o perf.csv

rawenter has two side effects. At full idle, the normal syscall path is the energy-efficient one (the runtime detects all-Ps-idle and puts sysmon to sleep, while rawenter keeps a 10ms wake-up, worth 0.1-0.3% CPU). And a thread blocked in a raw wait still shows as ordinary S (interruptible sleep) in ps, never D.

The S3710 over its USB bridge is bandwidth-bound, and even synchronous v1 keeps up (at QD1 sequential, a serial server never leaves the device idle). GC, runtime fixed costs, and copy modes all vanish on a substrate whose ceiling is device bandwidth. 4K random is ruled by per-operation counts and structure; sequential bandwidth is leveled by the backend. The optimization priority order flips with the workload.

Lessons

  • A ublk server in pure Go, without cgo, is entirely practical. All it takes is the standard library's syscall package and a minimal io_uring layer (about 300 lines), and the result is a real block device that carries ext4. Add the lightness of scp-ing a single static binary into a VM, and Go is a genuinely workable choice for this kind of code.
  • pprof names every cause. The allocation profile pinned the GC (99.7% from one make) and the CPU profile pinned the synchronous serialization (71% waiting in pread), each in one shot. Starting from a guessed sync.Pool would have left the dominant bottleneck unnoticed.
  • GC damage lives in the upper tail, and load amplifies it. Taking 5719 GCs to 5 cut p99.9 by 40%, from 2311µs to 1385µs. Each pause is short, but 40 thousand requests per second pile into the queue while the world is stopped. Fittingly, the one configuration with a live GC (async-naive) was also the only one that dropped part of the offered 40k (effective 39.3k).
  • Tuned Go gets within reach of a Rust implementation. When IO dominates, the language gap barely shows, and the GC can be designed down to effectively zero collections. Go's remaining overhead is that sysmon (the runtime's watchdog) intervenes whenever it finds a thread waiting in a syscall; that cost the servers an extra 7.6 CPU points for the same 40k IOPS here, and cutting the intervention with RawSyscall brings Go back level with rublk at 32.9%. As long as IO waits dominate, the languages tie, but needing to care about runtime intervention is a real difficulty Go carries for microsecond-scale work.

Conclusion

A ublk server in pure Go, no cgo, built up one step at a time and measured on the S3710. Making the synchronous serial loop asynchronous took saturated IOPS from 4.3k to 52.5k; sync.Pool and fixed buffers cut the GC to effectively zero and p99.9 from 2311µs to 1385µs; RawSyscall stopped the runtime's intervention and brought CPU down to 32.9%, level with rublk. The final build performs on par with the Rust implementation, within about 2% of its saturated throughput.

In Go, the standard library suffices, a single static binary runs anywhere, and pprof plus runtime/metrics let you observe every corner of the server's behavior. Once the goal becomes shaving latency at microsecond granularity, you need design work to keep the GC and the runtime's interventions out of the way (fixed buffers, RawSyscall), and beyond that point Rust is the more straightforward tool. Still, at PoC scale, implementing a ublk device in Go is a perfectly reasonable choice.
