What Power-Loss Protection Buys: fsync Benchmarks of a Used Enterprise SSD vs. a Consumer NVMe

dm-snapshot's flush costs sent me to an auction for a used Intel DC S3710. The comparison is imperfect — no SATA slot left, so the S3710 sits behind a USB bridge — but with fdatasync on the write path the PLP drive still comes out ahead, and physical flush accounting shows why.

This experiment owes its existence to a slowdown. While making the blktrace animations for an earlier article, I watched dm-snapshot drag 4k random writes from 16,000 IOPS down to 430 the moment a snapshot existed. The per-step timing in that trace put roughly 90% of the latency on one thing: dm-snapshot persists its COW mappings with device cache flushes — up to two per COW cycle, depending on when the metadata needs updating — and on the consumer NVMe this machine uses, each one cost ~0.9ms. The writes were cheap. In that trace, the flushes were the workload.

There is a class of hardware built to make exactly that cost disappear: enterprise SSDs with power-loss protection (PLP) — capacitors that guarantee the volatile cache reaches NAND if power dies, which lets the drive answer a flush without actually doing anything. So I went to an auction and got a used Intel DC S3710: 400 GB, SATA, MLC, datacenter class, vintage 2015. Ten years old, but carrying the one spec-sheet line my NVMe lacks.

One confession before any numbers. The mini PC running these experiments has no free SATA slot, so the S3710 hangs off a JMicron USB bridge, while the FORESEE 512 GB NVMe — which also holds the root filesystem — sits on PCIe. This is not an identical-conditions comparison, and on this machine it cannot be one: every number the old drive posts carries a USB overhead of several tens of µs per command. The variable I want to isolate is the presence of PLP — not SATA versus NVMe, not 2015 versus now — and the asymmetric attachment contaminates exactly that isolation, in the PLP drive's disfavor. So the honest framing is a handicap match: can PLP's advantage still be observed through the handicap? It can: I gave both drives an identical file-backed stack, ran fio against it with and without sync, and watched the ranking invert. The rest of the article is the trail — the head-to-head numbers, the decomposition of why the NVMe wins the easy case, a 1→128 parallelism sweep, and physical flush accounting from /proc/diskstats to prove which layer serializes.

The rig

Both drives are measured through the same file-backed stack: a 10G file on each drive's own ext4, attached as a loop device. That is partly honesty about a constraint — the NVMe holds the root filesystem, so raw access is off the table — and partly experimental hygiene: whatever overhead the file and loop layers add, both drives pay it identically.

# one 10G backing file on each drive's own ext4, fully pre-written
dd if=/dev/zero of=$FILE bs=1M count=10240 oflag=direct conv=fsync

# loop devices with direct-io, so the host page cache never absorbs a write
losetup --find --show --direct-io=on $FILE

# fio talks to the loop devices directly, e.g.:
fio --filename=/dev/loopN --rw=randwrite --bs=4k --direct=1 \
    --ioengine=psync --fdatasync=1 --time_based --runtime=30

All measurements use fio 3.36, and every test is 4k random writes with direct=1 unless stated otherwise. The path a synced write travels: fio's fdatasync against the loop device → loop issues fdatasync on the backing file → ext4 journal commit → FLUSH command to the physical drive. That last hop is the one under test.

Without sync the modern drive does exactly what its spec sheet promises. Add one fdatasync per write and the ten-year-old USB-attached drive is 2.2× faster — its flush costs 392µs end to end while the NVMe's costs 1.1ms. Both drives run with their volatile write cache enabled; the difference is what a FLUSH command means to each. The S3710's cache is capacitor-backed, so acknowledging a flush costs almost nothing. The consumer drive has to actually drain its cache to NAND, every time.

Why does the NVMe win the easy case?

Before celebrating the old drive, I owed the 3.9× no-sync loss an explanation — is that the SATA-vs-NVMe protocol gap? Reads offer a second witness: 4k random reads at qd1 show the same shape of gap, 180µs against 58µs.

An unsynced write is acknowledged from volatile cache on both drives, so NAND speed is not even in the path — the ~100µs gap is pure command-path latency. It splits further with one measurement and one datasheet. The loop layer is measurable: writing a file directly on the NVMe side costs 24µs against 33µs through the loop, so the loop adds ~9µs and the NVMe device plus ext4 answer in ~24µs. The S3710's datasheet puts its typical write latency at 66µs — a native-SATA figure — so drive generation alone accounts for 40µs-plus of the gap before the USB bridge enters. Subtracting the 9µs loop and the 66µs spec from the measured 130µs leaves ~55µs riding on the USB bridge and its SCSI→SATA translation; how that residual divides between the bridge and the SATA/AHCI protocol itself cannot be determined without a native port. "NVMe is faster than SATA" is the least of it; "a PCIe-native modern controller beats a USB-bridged 2015 controller" is most of it.

At queue depth 1, IOPS is just 1/latency, so every one of those microseconds shows. Which raises the obvious next question: if the gap is a fixed per-command latency, does parallelism amortize it away?

1 to 128 writers

Two sweeps per drive. Without sync, parallelism means asynchronous queue depth (io_uring, iodepth=N). With sync it has to mean processes — fdatasync is a synchronous syscall, so the only way to have N flushes in flight is N writers (psync, numjobs=N, fdatasync=1). That distinction is the same one a database faces: you cannot "async away" a commit.

Parallelism does amortize the fixed latency — on the left panel the S3710 scales 6k→45k and plateaus (the USB/UAS queue depth of 30 is the likely ceiling), the NVMe scales to ~93k, and the ratio narrows from 3.9× to 2.1×. But it never closes, and sequential 1M transfers make it worse (435 vs 2,250 MiB/s): once per-command latency is amortized, the bottleneck moves to link bandwidth, and SATA's 6 Gb/s is a hard wall while PCIe keeps going.

The right panel is the article. With a flush after every write, the S3710 scales almost linearly to 29k IOPS at N=64 — parallel writers pipeline cleanly because each flush is nearly free. The NVMe crawls under 1,000 IOPS until N=8, and only starts climbing when enough writers pile up that the kernel can merge their flushes (more on that mechanism below). At N=128 it has clawed back to 10k — still a third of the PLP drive, on a device that is 2× faster at everything else.

The instability bonus. The NVMe's sync numbers are not just low, they are erratic: re-running the N=2 point three times gave 194, 567, and 949 IOPS — a 5× spread, presumably tracking SLC-cache and garbage-collection state, since a flush costs whatever "drain the cache now" costs at that moment. The S3710 under the same re-runs: 2,766 / 2,777 / 2,788 — a ±0.4% band. Attributing that stability to PLP alone would overreach, though. A near-no-op flush cannot vary much, so in that sense it follows from PLP — but the variance on the NVMe side comes from SLC caching and garbage collection, which are consumer-design traits, and the S3710 is an enterprise drive engineered for latency consistency well beyond its capacitors. The speed gap belongs to PLP; the consistency gap belongs to the enterprise-versus-consumer design difference as a whole, of which PLP is one part. For a latency SLO, that consistency may matter even more than the speed.

"Isn't the loop device just serializing your flushes?"

A fair objection: both drives sit under loop devices and ext4, and the jbd2 journal famously serializes commits. Maybe the NVMe's flatline is the stack's fault, not the drive's. Two answers, one logical and one measured.

The logical one: the stack is byte-for-byte identical on both sides, and the PLP side pushes 29k sync writes per second through it. If loop+jbd2 serialization capped throughput at ~800 IOPS, it would cap both drives.

The measured one: since kernel 5.5, /proc/diskstats counts FLUSH commands and their ticks per physical device (fields flush_ios/flush_ticks), so you can watch flushes arrive at the actual drive while fio runs upstream:

The serialization point is visible and it is not the loop: at 8 writers the NVMe spends 71% of wall-clock time executing FLUSH commands, each taking ~0.7ms (and multiple milliseconds on bad days). A cache flush is inherently a device-wide, serialized operation — that is what parallel writers queue behind. The S3710's flushes take 0.16ms flat, independent of load.

The table also shows the stack actively helping both drives rather than hurting them: fio completes more sync writes than the device receives flushes (9,745 ops on 3,384 flushes; 4,117 on 1,012), because jbd2 group commit merges concurrent fdatasyncs into one journal commit and one flush. That merging is exactly why the NVMe's curve finally lifts at high N — and it is the same group-commit machinery a real database relies on. (It is also why this NVMe run shows 4,117 IOPS where the sweep recorded 754: the drive's flush cost had a good ten seconds. See the instability callout above.)

One suspicion the table cannot fully retire. The S3710 hangs off a USB bridge, and bridges that drop or "optimize" FLUSH instead of forwarding it are a real, long-documented phenomenon — if this JMicron does that, the cheap flushes would be the bridge slacking, not PLP working. The measurements are only circumstantial evidence against it: a swallowed flush should complete in ~0µs, while the observed 0.16ms matches a USB round trip, and it stays at 0.16ms under load, with no dependence on how much dirty data there is to drain. That is consistent with "the flush reaches a drive that can answer it cheaply" — but it is not distinguishable, from the outside, from a bridge that acknowledges after a fixed delay. Settling it would take a pull-the-plug data-loss test (in the spirit of diskchecker.pl) or a native SATA re-run, and I have done neither here. The conclusion stands on the S3710 behaving as its PLP spec says it should; treat it with that reservation.

What PLP actually buys

Power-loss protection is a bank of capacitors that guarantees the drive's volatile cache reaches NAND if power dies. The performance consequence follows directly from the guarantee: a drive that cannot lose its cache is allowed to treat cache-resident data as durable — so a FLUSH command, whose entire meaning is "make the cache durable, now", is already satisfied when it arrives. The S3710 answers in a USB round trip. The FORESEE has no such guarantee, so each FLUSH forces NAND programming of whatever is dirty: milliseconds, serialized, at the mercy of the drive's internal state.

Where does that bite? Everywhere durability is on the write path: database commit logs (a qd1 fsync loop is precisely pg_test_fsync's shape), etcd/raft WALs, filesystem journals, message-queue acks, anything that promises "this write survived" before answering the network. The exception the data grants is honest, too: for sequential bulk writes with an occasional flush — 1M blocks with fdatasync each — the NVMe still wins (499 vs 351 MiB/s), because one flush amortized over a megabyte is noise and bandwidth decides. If your workload is streaming backups, buy bandwidth. If it answers "committed" to anyone, per-flush cost is the workload — and under this stack, that cost difference was large enough to outweigh a USB bridge, a SATA link, and ten years of controller progress combined.

To be clear about what this is not: a recommendation to hang used SATA drives off USB bridges. PLP is not a relic of the SATA era — current datacenter NVMe and industrial SSDs ship with it as a standard feature, buyable new, with none of this experiment's handicaps. The auctioned S3710 was the cheapest way to isolate one variable, the presence of PLP, on hardware I could afford to be wrong about. If sync writes decide your performance, the practical takeaway is to put a current PLP drive on a native interface; the numbers here are a lower bound on what that buys.

Caveats, so the numbers travel well. The NVMe also hosts the root filesystem — background system writes share the device, though the 10-second windows were dominated by the benchmark (~10⁴ flushes vs ~10² of noise). The loop layer adds ~9µs per op (measured) and jbd2 group commit shapes both sync curves equally; absolute numbers are stack-specific, the asymmetry is the drives'. The sweep points are single 10s runs — fine for the PLP side (±0.4%), a snapshot of a moving target for the NVMe (see instability). And the S3710's USB bridge inflates its per-command latency by roughly 50µs, meaning a natively attached S3710 would look better than every PLP number here.

The open question I could not close on this machine: how much of the S3710's remaining latency is the USB bridge versus the 2015 controller. That needs a native SATA port, and this box has none free — if I ever move the drive, the qd1 columns get a follow-up.
