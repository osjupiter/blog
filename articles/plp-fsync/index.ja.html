PLP は fsync をどれだけ速くするのか: 中古エンタープライズ SSD とコンシューマ NVMe の比較

dm-snapshot の flush コストをきっかけに、オークションで中古の Intel DC S3710 を入手しました。SATA スロットの空きがなく USB ブリッジ経由という不利な接続でも、fdatasync を伴う書き込みでは PLP 付きドライブが優位でした。その理由を物理 FLUSH の計測で確かめます。

この実験は、以前の記事で見つけた遅さから始まりました。blktrace のアニメーションを作っていたとき、dm-snapshot にスナップショットを作らせた途端、4k ランダム書き込みが 16,000 IOPS から 430 まで落ちたのです。あのときの trace でステップごとの所要時間を測ると、レイテンシの約 9 割を flush が占めていました。dm-snapshot は COW のマッピングを永続化するためにデバイスキャッシュの flush を発行します。回数はメタデータ更新のタイミングに依存し、COW 1 サイクルあたり最大 2 回です。このマシンのコンシューマ NVMe では、その 1 回に約 0.9ms かかっていました。write そのものは十分速く、少なくともあの trace では、時間のほとんどを flush が占めていたことになります。

flush のコストを下げるために作られたハードウェアがあります。電源断保護(PLP)付きのエンタープライズ SSD です。PLP は、電源が落ちても揮発キャッシュの内容が NAND に書き切られることをコンデンサで保証する仕組みで、この保証を持つドライブは flush を受け取っても実際にはほとんど何もする必要がありません。そこでオークションで中古の Intel DC S3710 を入手しました。2015 年発売の 400 GB SATA、MLC のデータセンター向けドライブです。10 年前の製品ですが、手元の NVMe にはない PLP を備えています。

数字を見せる前に、条件について断っておくことがあります。実験機の mini PC には SATA スロットの空きがなく、S3710 は JMicron の USB ブリッジ経由でつなぐしかありませんでした。比較相手の FORESEE 512 GB NVMe(ルートファイルシステムと同居)は PCIe 直結です。つまり接続条件は対等ではなく、このマシンでは対等にできません。S3710 側の数字には、コマンド 1 回あたり数十 µs の USB オーバーヘッドが常に乗っています。分離したい変数は PLP の有無であって、SATA と NVMe の差でも新旧の差でもありません。ところが接続の非対称は、まさにその分離を PLP 側に不利な形で汚します。だからこの記事にできるのは公平な比較ではなく、ハンデ込みでも PLP の強みが観測できるかを確かめることまでです。結果から言えば観測できました。それも、予想よりずっと大きな差でした。以下、同一のファイル+loop 構成に対する fio の結果、sync なしで NVMe が速い理由の分解、並列度 1〜128 のスイープ、そして直列化がどの層で起きているかの /proc/diskstats による確認、の順に記録します。

実験装置

測定は 2 台とも、同じファイル+loop の層を通して行います。各ドライブ自身の ext4 に置いた 10G のファイルを、loop デバイスとしてアタッチする構成です。一つには制約への正直さとして(NVMe はルートファイルシステムを載せているので、生デバイスでは測れません)、もう一つは実験の作法として。ファイルと loop の層で生じるオーバーヘッドが何であれ、2 台が同じだけ払うことになるからです:

# one 10G backing file on each drive's own ext4, fully pre-written
dd if=/dev/zero of=$FILE bs=1M count=10240 oflag=direct conv=fsync

# loop devices with direct-io, so the host page cache never absorbs a write
losetup --find --show --direct-io=on $FILE

# fio talks to the loop devices directly, e.g.:
fio --filename=/dev/loopN --rw=randwrite --bs=4k --direct=1 \
    --ioengine=psync --fdatasync=1 --time_based --runtime=30

測定は fio 3.36 で、断りがない限りすべて 4k ランダム書き込みの direct=1 です。sync 付き書き込みが通る経路を並べておくと、fio が loop デバイスに fdatasync → loop が backing ファイルに fdatasync → ext4 のジャーナルコミット → 物理ドライブへの FLUSH コマンド、となります。測りたいのはこの最後の区間です。

sync なしでは、新しいドライブが期待どおりに勝ちます。ところが write 1 回ごとに fdatasync をはさむと、USB 接続の 10 年前のドライブのほうが 2.2 倍速くなりました。flush 1 回の所要時間は、S3710 が 392µs、NVMe が 1.1ms です。揮発ライトキャッシュはどちらも有効なので、差が出るとすれば FLUSH コマンドを受けたときの振る舞いです。S3710 のキャッシュはコンデンサで保護されているため、flush にはほとんど何もせずに応答できます。一方のコンシューマドライブは、flush のたびに実際にキャッシュを NAND へ書き出す必要があります。

sync なしで NVMe が速い理由

先に、sync なしの 3.9 倍差のほうを説明しておきます。これは SATA と NVMe というインターフェースの差なのでしょうか。手がかりとして同条件の 4k ランダム読み込みを測ると、S3710 側 180µs、NVMe 側 58µs と、書き込みと同じ形の差が出ます。

sync なしの write は両ドライブとも揮発キャッシュに載った時点で応答が返るため、NAND の書き込み速度はこの差に関係しません。残るのはコマンドが往復する経路そのもので、約 100µs の差は実測とスペックである程度まで割れます。まず loop 層のコストは実測できます。NVMe 側でファイルを直接叩くと 24µs、loop 越しでは 33µs なので、loop の取り分は約 9µs、NVMe デバイスと ext4 の応答は約 24µs です。次に S3710 のスペック上の典型 write レイテンシは 66µs で、これはネイティブ SATA での値です。つまり USB を挟む前に、コントローラの世代差だけで 40µs 強の差が出る計算になります。実測の 130µs から loop の 9µs とスペックの 66µs を引いた残り約 55µs が、USB ブリッジと SCSI から SATA への変換に載っている分です。この残差のうちどこまでがブリッジでどこからが SATA/AHCI 自体なのかは、ネイティブポートで測らない限り分離できません。「NVMe だから速い」というより、「PCIe 直結の現代のコントローラが、USB 越しの 10 年前のコントローラより速い」というのが実態でした。

キュー深度 1 では IOPS がレイテンシの逆数そのものになるので、この µs 単位の差がそのまま数字に表れます。では、差が固定の往復時間なのだとすれば、並列にすれば埋まるのでしょうか。

並列度 1〜128 のスイープ

ドライブごとに 2 種類のスイープを回します。sync なしの並列度は、io_uring の iodepth、つまり非同期に積むキューの深さで作ります。sync ありの並列度はプロセス数で作るしかありません。fdatasync は同期システムコールなので、flush を N 個同時に発行するには N 個のライターが必要だからです(psync, numjobs=N, fdatasync=1)。データベースのコミットが並列化しにくいのも、これと同じ理由です。

固定レイテンシの差は、並列度である程度まで薄まります。左のパネルでは、S3710 が 6k から 45k までスケールして頭打ちになり(上限はおそらく USB/UAS のキュー深度 30)、NVMe は 9.3 万まで伸びます。比率は 3.9 倍から 2.1 倍まで縮みますが、なくなりはしません。また、シーケンシャル 1M 転送では差がむしろ 5 倍に開きます(435 MiB/s に対し 2,250 MiB/s)。コマンド往復の時間が薄まった先ではリンク帯域が効いてきて、SATA の 6 Gb/s が超えられない上限になるからです。

本題は右のパネルです。write ごとに flush を打つ条件では、S3710 は N=64 で 29k IOPS までほぼ線形にスケールします。flush が軽いので、並列ライターの処理がきれいに重なるためです。NVMe は N=8 まで 1,000 IOPS 未満にとどまり、複数ライターの flush をカーネルがまとめられるようになって、ようやく伸び始めます(この仕組みは後述します)。それでも N=128 で 10k、PLP ドライブの 3 分の 1 です。

副産物の発見: ばらつき。NVMe の sync 性能は、低いだけでなく不安定です。N=2 の点を 3 回測り直すと 194、567、949 IOPS と 5 倍の幅が出ました。flush の所要時間は「その瞬間にキャッシュを書き出すコスト」なので、SLC キャッシュや GC の内部状態がそのまま結果に表れるのだと考えられます。同じ測り直しを S3710 で行うと 2,766 / 2,777 / 2,788 で、幅は ±0.4% に収まります。ただし、この安定性を PLP 単体の効果と呼ぶのは言い過ぎです。ほぼ no-op になった flush はブレようがない、という意味では PLP の帰結ですが、NVMe 側のブレを生んでいる SLC キャッシュや GC はコンシューマ設計の性質であり、S3710 はそもそもレイテンシの一貫性を狙って設計されたエンタープライズドライブです。速さの差は PLP に、ブレの差は PLP を含むエンタープライズとコンシューマの設計差全体に帰すのが公平でしょう。レイテンシの SLO を守る用途では、このブレの差がむしろ効くかもしれません。

loop デバイスが直列化しているのではないか

もっともな疑いです。どちらのドライブも loop デバイスと ext4 の下にあり、ext4 のジャーナル(jbd2)がコミットを直列化することはよく知られています。NVMe の頭打ちはスタックの制約であって、ドライブのせいではないのかもしれません。これには構成から言える反証と、実測による反証があります。

構成から言える反証: スタックは両側で完全に同一で、その同じスタックを PLP 側は毎秒 29k の sync write が通過しています。loop や jbd2 の直列化が毎秒 800 の頭打ちの原因なら、両方のドライブが同じ場所で止まるはずです。

実測による反証: kernel 5.5 以降の /proc/diskstats には、物理デバイスごとの FLUSH コマンド数と所要時間の累計が載っています(flush_ios と flush_ticks)。fio を動かしながらこれを差分すれば、実ドライブに届いた flush を数えられます:

直列化が起きている場所は、この表から読み取れます。8 並列のとき、NVMe は計測時間の 71% を FLUSH の実行に費やしています。1 回あたり 0.7ms で、内部状態によってはミリ秒台まで延びます。キャッシュ flush はデバイス全体に対する操作で、複数を同時には実行できません。並列ライターが待たされていた場所は loop ではなく、NVMe 自身の flush でした。S3710 の flush は負荷にかかわらず 0.16ms のまま変わりません。

この表からは、スタックがむしろ両者を助けていることも読み取れます。fio が完了した sync write の数より、デバイスに届いた flush の数のほうが少ないのです(9,745 ops に対し 3,384 flush、4,117 に対し 1,012)。同時に発行された fdatasync を、jbd2 のグループコミットが 1 回のジャーナルコミットと 1 回の flush にまとめているためです。NVMe の曲線が高並列でようやく持ち上がるのはこのまとめ書きの効果で、データベースが頼っている group commit と同じ機構です。(なお、この測定で NVMe がスイープ時の 754 に対して 4,117 IOPS を出しているのは、たまたま flush の所要時間が短い 10 秒間に当たったためです。前述のばらつきの一例です。)

もう一つの疑いは、この表でも完全には消せません。S3710 は USB ブリッジ越しで、FLUSH を転送せずに握り潰したり勝手に最適化したりするブリッジは、昔から実在が知られています。もしこの JMicron がそうなら、flush が安いのは PLP の効果ではなく、ブリッジがさぼった結果です。実測から言えるのは状況証拠までです。握り潰された flush はほぼ 0µs で完了するはずですが、実測は 0.16ms で USB の往復時間として妥当な値でした。負荷をかけても 0.16ms から動かず、掃き出すべきデータ量への依存も見えません。これは「flush は届いていて、PLP のおかげで安く済んでいる」という説明と整合しますが、「ブリッジが一定時間で ACK だけ返している」場合と外から区別はつきません。決着には、書き込み中に電源を抜いてデータ消失を確かめるテスト(diskchecker.pl の類)か、ネイティブ SATA での再測定が必要で、どちらも今回はできていません。この記事の結論は、S3710 が PLP の仕様どおりに振る舞っていることを前提にしています。その留保付きで読んでください。

PLP が何を変えるのか

電源断保護の実体はコンデンサです。電源が落ちても、ドライブは残った電力で揮発キャッシュの内容を NAND に書き切れます。性能への効き方は、この保証から直接導けます。キャッシュを失わないドライブにとって、キャッシュに載ったデータはすでに永続です。だから「キャッシュを永続化せよ」という意味しか持たない FLUSH コマンドは、届いた時点で完了しています。S3710 の応答時間は実質 USB の往復だけでした。FORESEE にはこの保証がないので、FLUSH のたびに dirty なデータの NAND への書き込みが走ります。ミリ秒単位で、直列で、内部状態に左右されながらです。

この差が効くのは、書き込みの完了と耐久性の保証が結びついている処理です。データベースのコミットログ(キュー深度 1 の fsync ループは pg_test_fsync が測る形そのものです)、etcd や raft の WAL、ファイルシステムのジャーナル、メッセージキューの ack。「書き込みは保存された」と応答してから先へ進む処理はすべて該当します。逆に、PLP が効かない領域も測定に表れています。1M ブロックの書き込みに fdatasync を 1 回ずつ添える条件では NVMe が勝ちました(499 MiB/s に対し 351 MiB/s)。1 MiB の転送時間に対して flush 1 回の重みは小さく、帯域の差が残るからです。大きな書き込みを流し続ける用途なら帯域を選ぶべきで、コミットを返す用途なら flush の単価がそのまま性能になります。今回のスタックでは、その単価の差が、USB ブリッジと SATA リンクと 10 年分のコントローラの進歩を合わせたハンデを上回った、というのが観測の中身です。

誤解のないように書いておくと、この記事は「中古の SATA ドライブを USB でぶら下げろ」という勧めではありません。PLP は SATA 時代の遺物ではなく、現行のデータセンター向け NVMe や産業用 SSD には標準的に載っていて、新品で普通に買えます。今回オークションの S3710 を選んだのは、PLP の有無というひとつの変数を、失敗しても惜しくない値段で検証するためです。sync 書き込みが性能を決める用途での実用的な結論は「現行の PLP 付きドライブをネイティブ接続で使う」で、この記事の数字はその効果の下限を示していることになります。

数字を引用するときの注意。NVMe はルートファイルシステムと同居しており、システムのバックグラウンド書き込みがデバイスを共有しています(ただし 10 秒の測定窓では flush 数がベンチマーク約 10⁴ に対しノイズ約 10² で、影響は小さいはずです)。loop の層は 1 操作あたり約 9µs(実測)を上乗せし、jbd2 のグループコミットは両方の sync 曲線に同じ形で効いています。絶対値はこのスタック固有のもので、持ち出せるのは 2 台の差のほうです。スイープの各点は 10 秒 1 回の測定で、ばらつきの小さい PLP 側には十分ですが、NVMe 側は揺れる値の 1 サンプルにすぎません。また S3710 の USB ブリッジはコマンドあたり約 50µs を上乗せしているので、ネイティブ SATA 接続で測り直せば、PLP 側の数字はここに載せたどれよりもよくなるはずです。

このマシンでは閉じられなかった問いが一つ残っています。S3710 のレイテンシのうち、どこまでが USB ブリッジで、どこからが 2015 年のコントローラなのか。切り分けにはネイティブの SATA ポートが必要で、この実験機にはありません。ドライブを別のマシンに挿す機会があれば、キュー深度 1 の列を測り直すつもりです。
