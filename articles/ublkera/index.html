ublkera: dm-era-style Change Tracking in Userspace with ublk

Rebuilding the kernel's dirty-block tracker as a multi-device userspace daemon — verification by three independent witnesses, queue/CPU scaling experiments, and a bug that only fires after you log out.

Linux has a driver called ublk that lets an ordinary process implement a block device: the kernel exposes /dev/ublkbN, and every request that hits it is handed to your userspace code to complete. I used it to build ublkera — a daemon that exposes any file or block device through ublk and layers dm-era-style change tracking on top of the passthrough. This article is half project write-up, half field notes on ublk itself: where it came from, how a request actually reaches userspace, what the queue/thread model means for CPU scaling, and the measurements and bugs along the way.

What is ublk?

ublk is an io_uring-based framework for userspace block drivers, added in Linux 6.0. It exists so that virtual block devices — loop-alikes, nbd-style devices, image formats like qcow2 — can be implemented as ordinary userspace programs; details are in the kernel documentation and the LWN write-up.

How a request reaches userspace

Both planes ride on io_uring. Control is a misc device, /dev/ublk-control: the server sends ADD_DEV (negotiating queue count, depth, buffer size), which creates a per-device char device /dev/ublkcN — the data-plane channel. The server mmaps the request-descriptor array, arms the data plane, then sends START_DEV; only at that point does the actual block device /dev/ublkbN appear.

The data plane is the elegant part. For each hardware queue the server runs a dedicated thread with its own io_uring, and at startup that thread submits one FETCH_REQ uring_cmd against /dev/ublkcN for every tag (request slot) in the queue. These commands don't complete — they wait. And the first fetch is what binds the queue to the thread: whichever thread fetched a (queue, tag) becomes the daemon for that slot, and from then on only it may issue commands for it.

One IO, one round trip: the pending fetch wakes exactly the right thread; the commit answers and re-arms in one step.

When an application IO hits /dev/ublkbN, blk-mq picks a queue and a free tag, and ublk_drv completes the pending fetch for that (queue, tag) — waking exactly the right server thread with zero routing logic in userspace. The thread reads the descriptor, performs the backing IO (in ublkera's case: another io_uring operation, against the backing file, on the same ring), and answers with COMMIT_AND_FETCH_REQ, which completes the block request and re-arms the tag in a single step. The steady state is a tight loop on one ring per queue: no per-IO syscalls beyond batched io_uring_enter, no thread handoffs, no locks shared between queues.

Why build ublkera?

In a previous article I used dm-era — the kernel's device-mapper target that tracks which blocks were written in which "era" — to do zero-downtime differential backups. It works, and I still like it. But living with it for a while left a list of ergonomic complaints:

  • Every tracked device is a dmsetup stack assembled by hand — an origin, a separate metadata LV, a table line with sector counts. Track ten devices and you have ten stacks, with nothing managing them as a group.
  • Reading the dirty map is not one query: snapshot the metadata LV, run era_dump against the snapshot, parse the XML. (Running a dump tool is table stakes for any tracker — the friction is the snapshot choreography around it, and the output format.)

What I actually wanted was an operational shape dm-era doesn't have: one resident process supervising change tracking for any number of block devices — attach and detach at runtime, one control socket, answers in JSON.

Look back at the ublk request loop above and the fix suggests itself: every write already passes through my process, so tracking dirty blocks is just bookkeeping on the side. ublkera is that idea as a single resident daemon — it exposes backing files or block devices as ublk devices, passes IO through 1:1, and records which chunks were written in which era, dm-era style. In Rust, on top of the libublk crate.

ublkera daemon (resident, control socket /run/ublkera/daemon.sock)
 ├─ device 0: supervisor thread ── /dev/ublkb0 ⇄ a.img   (era map + metadata)
 ├─ device 1: supervisor thread ── /dev/ublkb1 ⇄ b.img   (era map + metadata)
 └─ ... add / del at runtime

The workflow it replaces is pleasantly boring. Attach any file or block device at runtime and a /dev/ublkbN appears; everything speaks one-line JSON over a unix socket:

$ sudo ublkera add -f /data/a.img --meta /var/lib/ublkera/a.meta
{"ok":true,"dev_id":0,"bdev":"/dev/ublkb0","granularity":65536,"current_era":1}

$ sudo ublkera checkpoint -f /data/a.img       # close era 1, writes now stamp era 2
$ sudo ublkera dump -f /data/a.img --since 1   # byte ranges written since that checkpoint
{"ok":true,"ranges":[{"offset":33554432,"len":65536}],"dirty_bytes":65536}

Read the ranges from the device (or a snapshot of it), and you have your differential backup — same operational model as dm-era, one integer of bookkeeping, no XML, no metadata LV, no dmsetup tables.

How the tracking works

Each device keeps an in-memory array: one 32-bit "era this chunk was last written in" per chunk (chunk = granularity, default 64 KiB). The IO path is a strict 1:1 passthrough — one ublk request in, one io_uring operation on the backing file out:

ublk opbacking operationera map
READio_uring read at same offset/len—
WRITEio_uring write at same offset/lenstamp on completion
FLUSHfsync—
DISCARDfallocate(PUNCH_HOLE)stamp (contents changed!)
WRITE_ZEROESnot supported → -EINVAL—

Two details matter for correctness:

Stamping happens at completion, with fetch_max. The era number is written into the chunk slot only after the backing write finishes, using an atomic max. If a checkpoint races with an in-flight write, the write can only be attributed to the newer era — the failure mode is "a chunk is reported dirty one era too late, so it gets copied redundantly," never "a write is missed." The same safe-direction bias dm-era has.

DISCARD is a write, as far as tracking is concerned. A hole punch changes what the device reads back, so it must dirty the era map. Easy to forget, and a silent data-loss bug in a backup tool if you do.

Notably, the granularity never touches the IO path. A 4 KiB write into a 64 KiB chunk is passed through as a 4 KiB write; the 64 KiB unit exists only in the bookkeeping. ublkera never splits or merges requests — request sizing is the kernel's business (more on that below).

Verification: three witnesses that must agree

A change tracker has one job: report exactly the blocks that changed. Testing it with "write something, check it shows up" is too weak — the interesting bugs are over- and under-reporting. So the end-to-end test collects three independent records of the same truth and demands they match bit-for-bit:

  1. Create an empty backing file, expose it via ublk, fill the whole device with random data.
  2. Witness #1 — full-read hashes. Read the device end to end, SHA-256 per 64 KiB chunk, save as hash.before.
  3. Checkpoint (era 1 closes; writes now land in era 2).
  4. Pick 20 random chunks; write 4 KiB of fresh random data at a random offset inside each. Witness #2 — the write log: the exact chunk list we chose.
  5. Checkpoint again (freezes the diff), re-hash everything as hash.after. Chunks where before ≠ after are the ground truth of what changed.
  6. Witness #3 — the tracker. dump --since 1, expand the byte ranges to chunk numbers.
paste hash.before hash.after | awk '$2 != $4 {print $1}' > diff-hash.txt
ublkera dump -n 0 --since 1 | (expand ranges to chunk numbers) > diff-era.txt

diff diff-hash.txt diff-era.txt \
  && diff written-chunks.txt diff-era.txt \
  && echo "MATCH: hash diff == era diff == written chunks"

All three agree: 20 chunks written, 20 chunks changed by hash, 20 chunks reported by the tracker, same numbers. The partial-write case is covered for free — a 4 KiB write in the middle of a chunk must flip that whole chunk to dirty, and does.

Three traps in this seemingly simple test. (1) The hash block size must equal the tracking granularity, or the comparison is meaningless — the tracker can only ever answer in chunk units. (2) The era diff is formally a superset of the hash diff: rewriting identical data dirties the map but not the hash. Writing /dev/urandom makes a same-hash overwrite vanishingly unlikely, turning ⊇ into =. (3) Mixing O_DIRECT writes with buffered reads serves you stale page cache and phantom differences — drop caches (or use direct reads) before each hash pass.

What I learned about ublk

1. The max request size is really a preallocated buffer

A ublk server preallocates one buffer per in-flight request (per tag), and declares that size to the kernel at device creation. The kernel then advertises it as the device's max_hw_sectors_kb and never sends a larger request. The conventional default — ublksrv's and ublkera's — is 512 KiB, so a 4 MiB sequential write arrives as 8 × 512 KiB requests, each passed through as one backing write.

Is 512 KiB a protocol limit? No — it's a memory/throughput trade-off you own. Resident memory per device is queues × depth × buf_size (default 1 × 64 × 512 KiB = 32 MiB). I measured what the kernel actually accepts (6.8 guest):

declared buf sizemax_sectors_kb (effective)max_hw_sectors_kb (ceiling)
512K512512
1M10241024
2M12802048
4M12804096
16M128016384

The surprise in the middle column: past ~1.25 MiB you hit a different limit — the block layer's soft cap max_sectors_kb, which defaults to 1280 KiB for every block device, ublk or not. The hardware ceiling keeps growing with your buffer; the effective request size doesn't, unless you also raise the soft cap via sysfs (echo N > /sys/block/ublkbN/queue/max_sectors_kb). Two knobs, two owners.

2. One IO thread per queue — how ublk spends your cores

ublk runs one dedicated IO thread (with its own io_uring) per queue, and ublkera gives every device its own. Run several devices and the work is inherently spread across cores: devices share no execution resources — era stamping is one atomic operation per completion — so apart from the CPUs themselves and the kernel's own work, devices never contend with each other.

A single device can also be served by multiple threads: create it with several queues (ublk's nr_hw_queues; add -q N in ublkera) and each queue gets its own thread, with blk-mq mapping submitting CPUs onto queues. The default is one queue, which serializes the userspace side of that device onto one thread — at most about one core. If a hot device is CPU-bound, queues are the knob.

Two independent knobs are in play here, and they scale different things. Depth is the number of tag slots per queue — how many commands can be in flight at once on one thread. Queue count is the number of threads — how much CPU can serve the device:

Depth scales concurrency per thread; queue count scales threads across CPUs.

To be precise, a queue thread is not pinned 1:1 to a CPU — the scheduler is free to migrate it. The statement is about capacity: one thread can burn at most one core, so one queue caps the userspace side of one device at ~100% CPU. Give the device as many queues as there are busy submitting CPUs and the cap disappears.

Measured on a 4-vCPU QEMU guest, backing file on tmpfs (so RAM speed, not disk, is the ceiling), fio 4k randread with direct=1:

configurationdaemon CPU (all threads)IOPS
1 device, -q 1 (default)≈97% — one core, saturated49.6k
1 device, -q 4≈275% — four queue threads on four cores130k
2 devices, -q 1 each≈134% — one thread per device, different cores33k + 33k

Those iou-wrk-* rows are a bonus lesson: the backing file was opened without O_DIRECT (tmpfs doesn't support it), and buffered io_uring operations get punted to kernel io-wq workers — which themselves spread across cores. With O_DIRECT on a real disk that layer mostly disappears.

3. Cloud kernels don't ship ublk_drv

Small but time-consuming: Ubuntu cloud images don't include ublk_drv.ko — it lives in linux-modules-extra, which the cloud kernel flavor doesn't pull in. If your test VM is built from a cloud image, modprobe ublk_drv fails until you apt install linux-modules-extra-$(uname -r). Bake it into cloud-init and forget about it.

The project ended up with two QEMU-based test rigs, both rootless on the host: a busybox initramfs VM (host kernel + the daemon binary + ublk_drv.ko, boots and runs the full E2E suite in seconds) for CI-style checks, and a full Ubuntu cloud-image VM for interactive poking, provisioned by cloud-init with the module fix above. Real block devices need root somewhere; a VM keeps "somewhere" disposable.

The bug that only fires after you log out

One bug deserves its own section, because the mechanism is a classic. Symptom: the daemon runs fine, passes the full test suite… and the next day, every add fails with:

{"error": "device for '/root/cbt-test.img' did not come up within 15s"}

No device node, nothing in dmesg, and — the genuinely confusing part — a freshly started daemon on the same machine worked instantly. Only the long-running daemon was broken. strace on the daemon during an add found the smoking gun in two lines:

write(1, "\n", 1)                                = -1 EIO
write(2, "\nthread 'ublkera-dev-/root/cbt-t"..., 203) = -1 EIO

The device had actually come up fine. Then the "device ready" hook called a libublk helper that println!s a device summary to stdout. The daemon had daemonized with inherited stdio — still pointing at the pty of the ssh session that started it. When that session ended, the pty died; the next write to it returned EIO; and in Rust, a failed println! panics. The panic unwound the supervisor thread before it could report readiness, taking the freshly created device with it. Hence: works all day, breaks after you log out.

Three fixes, each independently worth having:

  • Daemonize with stdio detached to /dev/null — a background daemon holding its parent's terminal is a time bomb with a logout-shaped trigger.
  • No stdout printing anywhere in daemon-side code paths. Responses belong on the control socket; diagnostics belong in the log.
  • Distinguish "startup thread died" (ready-channel disconnected — report the panic immediately) from "startup is slow" (15s timeout). The misleading timeout message cost most of the debugging time.
The general lesson: any long-lived process that inherits a terminal fd has a latent failure scheduled for the moment that terminal closes — and in languages where a failed print is fatal (Rust's println!, Python's BrokenPipeError), it fails loudly, at a distance, with a stack trace pointing somewhere innocent.

dm-era vs ublkera

dm-eraublkera
where tracking runskernel (device-mapper target)userspace daemon (ublk)
setup per devicemetadata LV + dmsetup tableone add command, any file/device
attach / detach at runtimepossible, manual dmsetup surgerybuilt in (add/del, one daemon, N devices)
reading the dirty mapsnapshot metadata + era_dump → XMLdump --since N → JSON byte ranges
data pathin-kernel remap (near zero overhead)io_uring round trip through userspace
crash safety of the mapmetadata commits managed by kernelsaved at checkpoint/detach; crash loses the open era → take a full backup after a crash

The honest trade: dm-era keeps the data path in the kernel and its metadata is crash-consistent; ublkera pays a userspace round trip per IO and treats an unclean shutdown as "re-baseline." In exchange you get one daemon managing N devices, runtime attach of plain files, JSON instead of XML, and change-tracking logic you can read, test, and extend like any normal program — the whole verification section above is just shell scripts against a unix socket.

Conclusion

ublk turns "I wish the kernel tracked this for me" into "I'll track it myself, it's my process anyway." The passthrough-plus-bookkeeping pattern is a genuinely small program — the era map is an array of atomics and two rules (stamp on completion, stamp with max) — and the parts that took real effort were exactly the parts that always do: verification methodology, threading defaults, and a daemon lifecycle bug older than ublk itself.

Performance-wise, the userspace hop is not the bottleneck at backup-tool scale: one queue thread moves ~50k 4k IOPS on modest virtual hardware, queues scale it linearly across cores, and sequential IO passes through at full request size. If you need dm-era semantics in shapes dm-era is awkward about — devices that come and go, a fleet of them managed by one supervisor — building on ublk is a very reasonable place to stand.

Tested on Ubuntu 24.04 (guest kernel 6.8, QEMU/KVM, 4 vCPU) with fio 3.36. ublkera: Rust + libublk 0.4, granularity 64KiB, defaults -q 1 -d 64 -b 512K.
