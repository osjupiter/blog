ublkera: ublk で作るユーザ空間版 dm-era 風チェンジトラッキング

カーネルの dirty block トラッカーをマルチデバイス対応のユーザ空間デーモンとして作り直す — 3つの独立した証拠による検証とキュー/CPU スケーリング実験。

Linux には ublk というドライバがあり、普通のプロセスがブロックデバイスを実装できます: カーネルが /dev/ublkbN を公開し、そこに来るすべてのリクエストがユーザ空間のコードに渡されて、完了させるのは自分、という仕組みです。これを使って ublkera を作りました — 任意のファイル/ブロックデバイスを ublk 経由で公開し、パススルーの上に dm-era 風のチェンジトラッキングを重ねるデーモンです。この記事は半分がプロジェクトの記録、半分が ublk そのもののフィールドノートです: どこから来たのか、リクエストは実際どうやってユーザ空間に届くのか、キュー/スレッドモデルは CPU スケーリングにとって何を意味するのか、そして道中の実測。

そもそも ublk とは

ublk は Linux 6.0 で追加された、io_uring ベースのユーザ空間ブロックドライバのためのフレームワークです。loop や nbd、qcow2 のような仮想ブロックデバイスをユーザ空間のプログラムとして実装するためのもので、詳細はカーネルドキュメントと LWN の解説にあります。

リクエストがユーザ空間に届くまで

制御もデータも io_uring に乗っています。制御プレーンは misc デバイス /dev/ublk-control で、サーバが ADD_DEV(キュー数・深さ・バッファサイズを交渉)を送ると、デバイスごとのキャラクタデバイス /dev/ublkcN — データプレーンのチャネル — が生まれます。サーバはリクエストディスクリプタ配列を mmap してデータプレーンを準備し、START_DEV を送る。実際のブロックデバイス /dev/ublkbN が現れるのはこの時点です。

エレガントなのはデータプレーンです。HW キューごとにサーバは専用スレッドを1本立て、それぞれが自分の io_uring を持ちます。起動時にそのスレッドは、キュー内の全タグ(リクエストスロット)について FETCH_REQ という uring_cmd を /dev/ublkcN に対して発行します。このコマンドは完了しません — 待つのです。そして最初の fetch こそがキューとスレッドを紐づける操作です: ある (queue, tag) を fetch したスレッドがそのスロットのデーモンになり、以降そのスロットへのコマンドを発行できるのはそのスレッドだけになります。

IO 1つ = 往復1回。待っていた fetch が正しいスレッドだけを起こし、commit が応答とタグの再アームを1ステップで行う。

アプリの IO が /dev/ublkbN に来ると、blk-mq がキューと空きタグを選び、ublk_drv がその (queue, tag) で待っていた fetch を完了させます — ユーザ空間側のルーティングロジックはゼロのまま、正しいサーバスレッドだけが起きるわけです。スレッドはディスクリプタを読み、バッキング IO を行い(ublkera の場合: 同じリング上でバッキングファイルへの io_uring 操作をもう1発)、COMMIT_AND_FETCH_REQ で応答します。これはブロックリクエストの完了とタグの再アームを1ステップでやります。定常状態はキューごとにリング1本のタイトなループです: IO ごとの syscall はバッチされた io_uring_enter 以外になく、スレッド間の受け渡しもなく、キュー間で共有するロックもありません。

なぜ ublkera を作ったか

以前の記事では dm-era — どのブロックがどの「era」に書かれたかを追跡する device-mapper ターゲット — を使って、無停止の差分バックアップをやりました。ちゃんと動きますし、今でも気に入っています。ただ、しばらく使っていると使い勝手への不満が溜まってきました:

  • トラッキング対象1つごとに dmsetup のスタックを手で組む必要がある — origin、別建ての metadata LV、セクタ数入りのテーブル行。対象が10個あればそういうスタックが10本で、まとめて面倒を見てくれるものは何もない。
  • dirty map の読み出しがクエリ1発ではない: metadata LV をスナップショットし、それに対して era_dump を実行し、XML をパースする。(dump ツールを実行すること自体はどのトラッカーでも同じ — 面倒なのはその周りのスナップショットの段取りと、出力形式。)

本当に欲しかったのは、dm-era にはない運用の形です: 常駐プロセス1つが、任意の数のブロックデバイスのチェンジトラッキングを面倒見る — 実行中に attach/detach でき、制御ソケットは1本、答えは JSON で返る。

ここで上の ublk のリクエストループを思い出すと、答えは自明です: すべての書き込みはどのみち自分のプロセスを通るのだから、dirty block の追跡はただの「ついでの帳簿付け」です。ublkera はそのアイデアを常駐デーモン1つにしたものです — バッキングファイルやブロックデバイスを ublk デバイスとして公開し、IO を 1:1 でパススルーしながら、どのチャンクがどの era に書かれたかを dm-era 方式で記録します。Rust 製で、libublk クレートの上に載っています。

ublkera daemon (常駐、制御ソケット /run/ublkera/daemon.sock)
 ├─ デバイス0: supervisor thread ── /dev/ublkb0 ⇄ a.img   (eraマップ + メタデータ)
 ├─ デバイス1: supervisor thread ── /dev/ublkb1 ⇄ b.img   (eraマップ + メタデータ)
 └─ ... 実行中に add / del

置き換わったワークフローは気持ちよく退屈です。実行中に任意のファイル/ブロックデバイスを attach すると /dev/ublkbN が生え、すべて unix ソケット上の1行 JSON で会話できます:

$ sudo ublkera add -f /data/a.img --meta /var/lib/ublkera/a.meta
{"ok":true,"dev_id":0,"bdev":"/dev/ublkb0","granularity":65536,"current_era":1}

$ sudo ublkera checkpoint -f /data/a.img       # era 1 を閉じる。以降の書き込みは era 2
$ sudo ublkera dump -f /data/a.img --since 1   # その checkpoint 以降に書かれたバイトレンジ
{"ok":true,"ranges":[{"offset":33554432,"len":65536}],"dirty_bytes":65536}

ranges をデバイス(またはそのスナップショット)から読めば差分バックアップになります。運用モデルは dm-era と同じで、控えるのは整数1個。XML も metadata LV も dmsetup テーブルもありません。

トラッキングの仕組み

各デバイスはメモリ上に「このチャンクが最後に書かれた era」を表す 32bit 値の配列を1本持ちます(チャンク = granularity、既定 64 KiB)。IO パスは厳密な 1:1 パススルーで、ublk リクエスト1個に対しバッキングファイルへの io_uring 操作1発が対応します:

ublk opバッキング側の操作era マップ
READ同じ offset/len で io_uring read—
WRITE同じ offset/len で io_uring write完了時に刻印
FLUSHfsync—
DISCARDfallocate(PUNCH_HOLE)刻印(内容が変わるので!)
WRITE_ZEROES未対応 → -EINVAL—

正しさのために効いている点が2つあります:

刻印は完了時に、fetch_max で行う。 era 番号がチャンクのスロットに書かれるのはバッキングへの書き込みが完了した後で、しかもアトミックな max 演算です。checkpoint と実行中の書き込みが競合しても、その書き込みはより新しい era に帰属することしかできません。つまり失敗モードは「1 era 分遅れて dirty と報告され、余分にコピーされる」であって、「書き込みを取りこぼす」ことはない。dm-era と同じ安全側への倒し方です。

トラッキング上、DISCARD は書き込みである。 hole punch はデバイスの読み出し内容を変えるので、era マップを dirty にしなければなりません。忘れやすく、忘れるとバックアップツールとしては静かなデータロスバグになります。

注目してほしいのは、granularity が IO パスに一切触れないことです。64 KiB チャンクへの 4 KiB 書き込みは 4 KiB のままパススルーされ、64 KiB という単位は帳簿の中にしか存在しません。ublkera はリクエストを分割も結合もしません — リクエストサイズはカーネルの領分です(後述)。

メタデータのルールは1つだけです: 揮発性であり、失われてもバックアップを壊してはならない。era マップはメモリ上にあり、--meta 指定時は checkpoint とデタッチで保存されます。attach 中のファイルには「未クローズ」マークが付いていて、デーモンが不意に死ぬと、次の attach がそれを検知してデバイス全体を変更扱いにします("recovered_unclean": true)— 利用側の次の「増分」は自動的にフルコピーになります。消えた履歴に対する古いカーソルも、空の差分ではなくエラーで拒否されます。差分バックアップ用途ではこれが正しいトレードです: どんなクラッシュでも最悪は「フルコピー1回ぶんの損」で済み、引き換えにジャーナルも、クラッシュ整合なコミットプロトコルも、データパス上の同期書き込みも、一切存在しません。

検証: 一致すべき3つの証拠

チェンジトラッカーの仕事はただ1つ、変わったブロックを過不足なく報告することです。「書いてみて、出てくるか見る」程度のテストでは弱すぎます — 面白いバグは過剰報告と過少報告だからです。そこで E2E テストでは、同じ真実についての独立した記録を3つ集め、ビット単位での一致を要求します:

  1. 空のバッキングファイルを作り、ublk で公開し、デバイス全体をランダムデータで埋める。
  2. 証拠 #1 — フルリードのハッシュ。 デバイスを端から端まで読み、64 KiB チャンクごとに SHA-256 を取って hash.before に保存。
  3. checkpoint(era 1 が閉じ、以降の書き込みは era 2 に入る)。
  4. ランダムに 20 チャンクを選び、各チャンクの内部のランダムな位置に 4 KiB の新しいランダムデータを書く。証拠 #2 — 書き込みログ: 選んだチャンクの一覧そのもの。
  5. 再度 checkpoint(差分を凍結)し、全体を再ハッシュして hash.after に。before ≠ after のチャンクが「実際に変わったもの」の正解データ。
  6. 証拠 #3 — トラッカー。 dump --since 1 のバイトレンジをチャンク番号に展開する。
paste hash.before hash.after | awk '$2 != $4 {print $1}' > diff-hash.txt
ublkera dump -n 0 --since 1 | (レンジをチャンク番号に展開) > diff-era.txt

diff diff-hash.txt diff-era.txt \
  && diff written-chunks.txt diff-era.txt \
  && echo "MATCH: hash diff == era diff == written chunks"

3つは一致しました: 書いたのは 20 チャンク、ハッシュが変わったのも 20 チャンク、トラッカーが報告したのも同じ 20 チャンク。部分書き込みのケースも自動的にカバーされます — チャンクの真ん中への 4 KiB 書き込みはそのチャンク全体を dirty にしなければならず、実際そうなりました。

単純に見えるこのテストに潜む3つの罠。 (1) ハッシュのブロック長はトラッキングの granularity と一致させること。トラッカーはチャンク単位でしか答えられないので、ずれると比較自体が無意味になります。 (2) era 差分は形式的にはハッシュ差分の上位集合です: 同一データの上書きはマップを dirty にしますがハッシュは変えません。/dev/urandom を書けば同一ハッシュの上書きはまず起こらず、⊇ が = になります。 (3) O_DIRECT の書き込みとバッファードの読み出しを混ぜると、古いページキャッシュを読んで幻の差分が出ます — 各ハッシュパスの前にキャッシュを落とす(か direct read を使う)こと。

ublk についてわかったこと

1. 最大リクエストサイズの正体は「事前確保バッファ」

ublk サーバは in-flight リクエスト1個(タグ1個)につきバッファを1本事前確保し、そのサイズをデバイス作成時にカーネルへ申告します。カーネルはそれをデバイスの max_hw_sectors_kb として広告し、それより大きいリクエストは送ってきません。慣習的なデフォルト(ublksrv も ublkera も)は 512 KiB なので、4 MiB のシーケンシャルライトは 512 KiB × 8 リクエストとして届き、それぞれがバッキングへの write 1発としてパススルーされます。

では 512 KiB はプロトコルの上限なのか? 違います — 自分で選ぶメモリとスループットのトレードオフです。デバイスあたりの常駐メモリは queues × depth × buf_size(既定 1 × 64 × 512 KiB = 32 MiB)。カーネルが実際に何を受け付けるかを実測しました(ゲストカーネル 6.8):

申告したバッファサイズmax_sectors_kb(実効)max_hw_sectors_kb(上限)
512K512512
1M10241024
2M12802048
4M12804096
16M128016384

驚きは真ん中の列です: 約 1.25 MiB を超えると別の制限に当たります — ブロック層のソフト上限 max_sectors_kb で、これは ublk に限らず全ブロックデバイスで既定 1280 KiB です。HW 上限はバッファに合わせて伸び続けますが、実効リクエストサイズは sysfs でソフト上限も上げない限り(echo N > /sys/block/ublkbN/queue/max_sectors_kb)伸びません。ノブは2つ、持ち主も2人。

2. キューごとに 1 IO スレッド — ublk の CPU の使い方

ublk はキュー1本につき専用の IO スレッド(それぞれ自分の io_uring 付き)を立て、ublkera はデバイスごとにそれを持ちます。デバイスを複数生やせば、処理は必然的に複数のコアへ分散します: デバイス間で共有する実行資源はなく — era の刻印も完了ごとのアトミック演算1回だけ — CPU そのものとカーネル内の処理を除けば、デバイス同士が競合することはありません。

加えて、1つのデバイスを複数スレッドで処理することもできます: 複数キューで作成すれば(ublk の nr_hw_queues、ublkera では add -q N)キューごとにスレッドが立ち、blk-mq が発行元 CPU をキューへ割り当てます。既定はキュー1本で、その場合そのデバイスのユーザ空間側は1スレッド — 最大でも約1コア — に直列化されます。ホットなデバイスが CPU で頭打ちになったら、キュー数がノブです。

ここで効いているノブは2つあり、それぞれ別のものをスケールさせます。depth はキューあたりのタグスロット数 — 1本のスレッドで同時に in-flight にできるコマンド数です。キュー数はスレッドの本数 — デバイスの処理に使える CPU の量です:

depth は1スレッドあたりの並行度を、キュー数は CPU に広がるスレッド数をスケールさせる。

正確に言えば、キュースレッドが CPU に 1:1 で固定されるわけではありません — スケジューラは自由にスレッドを移動できます。これはキャパシティの話です: 1本のスレッドが燃やせるのは最大1コアなので、キュー1本は1デバイスのユーザ空間側を CPU 約100% で頭打ちにします。忙しい発行元 CPU の数だけキューを与えれば、この頭打ちは消えます。

4 vCPU の QEMU ゲスト、バッキングは brd(RAM ディスク — RAM 速度で、O_DIRECT も使える)、fio 4k randread direct=1 での実測:

1デバイス、-q 4≈214% — キュースレッド4本が4コアに188k

dm-era vs ublkera

dm-eraublkera
トラッキングの場所カーネル(device-mapper ターゲット)ユーザ空間デーモン(ublk)
デバイスごとのセットアップmetadata LV + dmsetup テーブルadd コマンド1発、任意のファイル/デバイス
実行中の attach / detach可能だが手動の dmsetup 手術組み込み(add/del、1デーモンで N デバイス)
dirty map の読み出しmetadata をスナップショット + era_dump → XMLdump --since N → JSON のバイトレンジ
データパスカーネル内リマップ(ほぼゼロオーバーヘッド)ユーザ空間経由の io_uring 往復
マップのクラッシュ耐性カーネルが metadata コミットを管理設計として揮発性: 不意の停止後は次の attach が全域を変更扱いにする — 次の差分が自動的にフルコピーになる

正直なトレードオフはこうです: dm-era はデータパスがカーネル内に留まり、メタデータはクラッシュ整合。ublkera は IO ごとにユーザ空間往復のコストを払い、メタデータを使い捨てとして扱います — 不意の停止の後は、次の差分が自動的にフルコピーになるだけ。その代わりに得られるのは、1デーモンで N デバイスの管理、ただのファイルへの実行時 attach、XML の代わりの JSON、そして普通のプログラムと同じように読めて・テストできて・拡張できるチェンジトラッキングのロジックです — 上の検証の節は、全部 unix ソケットに向けたシェルスクリプトでできています。

まとめ

ublk は「カーネルがこれを追跡してくれたらいいのに」を「自分のプロセスなんだから自分で追跡すればいい」に変えてくれます。パススルー + 帳簿付けというパターンは本当に小さなプログラムで済み — era マップはアトミック値の配列と2つのルール(完了時に刻印、max で刻印)だけ — 本当に手間がかかったのは、いつも手間がかかるところでした: 検証の方法論とスレッドのデフォルトです。

性能面では、バックアップツールの規模においてユーザ空間経由はボトルネックになりません: キュースレッド1本で控えめな仮想ハードウェア上でも 4k IOPS 約5万、キューを増やせばコア数までほぼ線形に伸び、シーケンシャル IO はリクエストサイズのままパススルーされます。dm-era が苦手とする形 — 出たり消えたりするデバイス、1つのスーパーバイザで管理したいデバイス群 — に dm-era のセマンティクスが欲しいなら、ublk の上に建てるのはかなり妥当な立地です。

Ubuntu 24.04(ゲストカーネル 6.8、QEMU/KVM、4 vCPU)+ fio 3.36 で検証。 ublkera: Rust + libublk 0.4、granularity 64KiB、既定値 -q 1 -d 64 -b 512K。
