LinuxブロックI/Oの可視化：LVM・ZFS・Btrfsは実際どのようにディスクへ書き込むのか

blktraceで記録したI/Oをアニメーション可視化し、ストレージスタックごとのwrite amplification（書き込み増幅）、COWの挙動、スナップショットのオーバーヘッドを観察します。

この記事について

ファイルに4KBを書き込んだとき、実際にディスクへ届くのは何バイトでしょうか？答えはストレージスタック次第で、しばしば予想を裏切ります。QEMU VM内のさまざまなLinuxストレージ構成に対して fio のランダム書き込みを実行し、すべてのブロックI/Oイベントを blktrace で記録して、その結果をアニメーション化しました。

以下の可視化に現れるドットの一つひとつが、実際のI/O完了イベントです。Y軸はディスク上の物理セクタを表し、ドットは時間の経過とともに左から右へ流れていきます。それぞれの書き込み（および読み取り)が、物理デバイス上のどこに・いつ着地したのかを正確に見て取ることができます。

実験環境：QEMU/KVM VM（4 vCPU、4GB RAM）。10GBのvirtioディスク2台。I/Oスケジューラは none、順序を決定的にするため fio は --iodepth=1 --direct=1 で実行。すべてのI/Oは物理ブロックデバイス上で blktrace により記録しています。

実験1：LVMリニア vs dm-thin

まずは最もシンプルな比較です。素のLVM論理ボリューム（リニアマッピング）と、シンプロビジョニングされたLVを比べます。同じランダム4KB書き込み、同じシード、同じ実行時間です。

dm-linear は最も単純なdevice-mapperターゲットです。セクタアドレスに固定オフセットを加算し、I/Oをそのまま物理デバイスへ渡します。ルックアップもメタデータもオーバーヘッドもありません。4KBの書き込みは、ディスク上でもきっかり1回の4KB書き込みになります。

dm-thin は間接参照の層を1つ追加します。書き込みのたびにbtreeをルックアップして物理ブロックを特定します。ブロックがすでにマップ済みならそのままリマップされます（高速パス）。未マップなら、プールのスペースマップから新しいブロックが割り当てられ、btreeとスペースマップの両方が更新されます。これらのメタデータ変更はまとめられ、およそ1秒ごとにディスクへコミットされます。コミット中（約50〜100ms）は書き込みロックがかかり、新しいI/Oはすべてルックアップをブロックされます。

LinearThin
書き込みイベント数171,284 WS78,400 WS + 29,844 W
IOPS~17,000~10,500
追加I/Oなし約3万件のメタデータ書き込み（64KBチャンク）

リニアはほぼ1:1です。fioが4KBを書けば、ディスクにも4KBが書かれます。一方シンプロビジョニングでは、チャンクを新規割り当てするたびにメタデータ書き込み（オレンジのドット）が発生します。thinプールは64KBチャンクを使うため、各チャンクへの初回書き込みごとにメタデータ更新が走るのです。

thin側では、およそ1秒ごとに約100msの停止が周期的に見られます。これはdm-thinのトランザクションコミットです。メタデータbtreeの更新をまとめてディスクへフラッシュしており、コミットの間はデータI/Oがブロックされます。

実験2：LVMスナップショット — COW vs ROW

スナップショットを取ってそのまま書き込み続けると、何が起きるのでしょうか？通常の（リニア）LVをスナップショットすると、LVMは dm-snapshot を使います。これは書き込みをインターセプトして Copy-on-Write（COW）を行うカーネルモジュールで、ブロックを上書きする前に古いデータを読み出し、別領域へコピーします。thin LVのスナップショットは Redirect-on-Write（ROW）という別の方式です。古いデータをコピーする代わりに、新しいデータを新しい場所へ書き込み、メタデータのポインタをそちらへ向け直します。

dm-snapshot（COW）は、上書きする前に古いデータを保全しなければなりません。書き込みごとに、古いブロックを読み出し、COW領域へコピーし、コピーの永続化を保証するためにフラッシュし、マッピングテーブルを更新し、再度フラッシュし、それからようやく新しいデータを書き込みます。書き込み1回につきフラッシュ2回（各約1ms）を含む、6ステップの直列処理です。

dm-thin（ROW）はこれらをすべて回避します。もともと間接的なブロックマッピングを使っているため、スナップショットは現在のメタデータポインタを凍結するだけで済みます。新しい書き込みは新規割り当てブロックへ向かい、ポインタが更新されます。古いブロックはスナップショット用に手つかずのまま残ります。古いデータの読み出しもコピーも、書き込みごとのフラッシュもありません。メタデータはこれまでどおりバッチでコミットされます。

その差は劇的です。スナップショット後、リニア側のパネルがほぼ停止し、ドットが極端にまばらになる点に注目してください。37倍のスローダウンは単なる数字ではありません。thin側が画面をアクティビティで埋め尽くす同じ時間の間、リニア側はほとんど何も書けていないことが目で確認できます。スナップショット前の書き込みが速いのは、デバイス内部の揮発性キャッシュが書き込みを吸収してくれるからです（約16k IOPS）。スナップショット後は、dm-snapshotがCOWマッピングを永続化するために書き込みのたびにフラッシュを強制し、そのたびにデバイスキャッシュがドレインされます。このフラッシュが書き込みごとに約1msのレイテンシを加え、COWサイクルあたり2回のフラッシュにより、書き込みスループットはほぼゼロまで落ち込みます。

リニア + スナップショット（COW）thin + スナップショット（ROW）
スナップショット前のIOPS~16,000~14,600
スナップショット後のIOPS~430~13,600
スローダウン37x1.07x
スナップショット後の読み取りI/Oあり（COW読み取り）なし
LVMスナップショットのCOWは、ランダム書き込みに対して壊滅的に遅くなります。4KBの書き込み1回が6ステップのシーケンスになるのです：古いブロックを読む → COW領域へ書く → フラッシュ → COWマッピングテーブルを書く → フラッシュ → 新しいデータを書く。2回のフラッシュ（ライトバリア）は、元のブロックが上書きされる前にCOWマッピングが永続化されることを保証します。これがないと、クラッシュ時にスナップショットが破損しかねません。各ステップの実測タイミングは、R 約0.06ms、W 約0.08ms、フラッシュ 約0.9ms × 2 = 1.8msで、書き込みあたり合計約2msです。レイテンシの90%をフラッシュだけで占めており、これが約16k IOPSから約430への37倍のスローダウンを生んでいます。緑のドット（読み取り）はCOWのソース読み取りです。
なぜ他のスナップショット実装は書き込みごとにフラッシュしないのでしょうか？ dm-thinやZFS/Btrfsは、メタデータ更新を周期的なトランザクションコミットにまとめます（dm-thin 約1秒、ZFS 約5秒、Btrfs 約30秒）。そのためクラッシュ時には直近数秒分の書き込みを失う可能性がありますが、メタデータはコミット時にアトミックに更新されるため、スナップショットの一貫性は保たれます。dm-snapshotは、より安全だが遅い道を選びました。COW操作を1件ずつ、その場で永続化するのです。アプリケーションが fsync() を発行すればバッチ方式のシステムでもコミットが走りますが、fioが O_DIRECT だけを使う場合、コミットは強制されません。

余談：fsyncを加えるとどうなるか

上の37倍のスローダウンには、スナップショットなしのdm-linearがデバイスキャッシュを一切フラッシュしないという事情もあります。O_DIRECT だけではフラッシュは発生しないのです。書き込みごとに fsync を加える（fio --fsync=1）と、すべての実装がフラッシュを強制され、条件が揃います：

fsyncなしfsyncあり
リニア（スナップショットなし）17,900 IOPS806 IOPS
リニア + スナップショット422 IOPS315 IOPS
thin（スナップショットなし）10,900 IOPS784 IOPS
thin + スナップショット10,100 IOPS290 IOPS

この表からはいくつかのことが読み取れます。素のリニアにfsyncを加えると、IOPSは17,900から806へ落ちます（22倍）。これは純粋に、書き込みごとにデバイスキャッシュをフラッシュするコストです。dm-snapshotにfsyncを加えてもほとんど変わりません（422 → 315、1.3倍）。もともと書き込みごとにフラッシュしているからです。条件の揃うfsyncあり同士で比較すると、スナップショットCOWのオーバーヘッドは806 → 315 = 2.6倍で、これが古いブロックの読み取り・コピー・マッピングテーブル書き込みのコストに相当します。

dm-thinは違う顔を見せます。fsyncなしなら、スナップショットの影響はごくわずかです（10,900 → 10,100 IOPS）。ところがfsyncを加えると、thinは290 IOPSまで落ち、dm-snapshot（315）よりもさらに遅くなります。fsyncのたびにdm-thinのメタデータトランザクションコミット一式（フラッシュ3回）が強制されるためで、dm-snapshotのCOWあたり2回のフラッシュより多いのです。

全体を貫くパターンはこうです：デバイスフラッシュを引き起こす構成は、このSSDでは例外なく1,000 IOPSを下回ります。フラッシュのレイテンシ（コンシューマ向けNVMeで約1ms）が偉大な平準化装置であり、ストレージスタックがどれほど巧妙でも、デバイスがフラッシュできる速度より速くは書き込めません。前述の実験での劇的な差（17k vs 400 IOPS）の大部分は、どの構成が書き込みごとにフラッシュするのか、どの構成がバッチして先送りするのか、の違いなのです。

（補足：これらのフラッシュレイテンシはQEMUによるアーティファクトではありません。ホストのNVMe SSD上で同じテストを行っても約1.1msのフラッシュレイテンシが観測されます。これはコンシューマ向けTLC/QLC SSDとして典型的な値です。）

thinスナップショットはRedirect-On-Write（ROW）を採用しています。古いデータをコピーする代わりに、新しいデータは新しい場所へ書き込まれ、メタデータのポインタが更新されます。ただし、スナップショット後のthinパネルをよく見ると、緑のドット（読み取り）が現れています。dm-thinのチャンクサイズは64KBですが、fioの書き込みは4KBです。共有されている64KBチャンクに4KBの書き込みが当たると、dm-thinはチャンク全体を読み出して新しい場所へコピーし、そのうえで4KBの変更を適用しなければなりません。事実上、チャンクレベルのCOWです。チャンクサイズを書き込みサイズに合わせれば（例：lvcreate -T ... -c 4k）、これらの読み取りは完全に消えます。

実験3：ZFS vs Btrfs — COWファイルシステム

ZFSもBtrfsもcopy-on-writeファイルシステムです。すべての書き込みは新しい場所へ行われ、メタデータツリーは新しいポインタで更新されます。しかし実装の細部の違いが、まったく異なるI/Oパターンを生み出します。

ZFSは、データを固定サイズのレコード（デフォルト128KB）として管理します。4KBを書き込むと、ZFSは128KBのレコード全体を新しい場所へCOWしなければなりません。データレベルだけですでに32倍の増幅です。加えて、ブロックポインタのMerkleツリー的な構造（間接ブロック、dnode、uberblock）も更新され、それらもすべてCOWされます。書き込みはARCにキャッシュされ（O_DIRECTは無視されます）、約5秒ごとのトランザクショングループ（TXG）で、ディスクのmetaslab全体に広がる大きなシーケンシャルバッチとしてフラッシュされます。

Btrfsは可変サイズのエクステントを使います。4KBの書き込みは、ブロックグループ内の次の空き位置に、ちょうど4KBのエクステントを割り当てます。古いエクステントは解放されます（スナップショットが参照していれば保持されます）。メタデータ更新（extentツリー + チェックサムツリー）は、16KBブロックとして別途COWされます。アロケータはブロックグループ内を順に前進するため、コンパクトでほぼシーケンシャルな物理書き込みパターンとなり、増幅は約1.0倍にとどまります。

ZFSBtrfs
fioの論理書き込み量~450 MB~445 MB
物理書き込み量10,449 MB~445 MB
書き込み増幅率~23x~1.0x
I/Oパターン10GBディスク全体に分散シーケンシャル、単一領域

なぜZFSは要求の23倍も書き込むのか

原因はZFSのデフォルト設定 recordsize=128KB です。fioがレコードに4KBを書き込むと、ZFSは128KBのレコード全体を新しい場所へCOWします。メタデータを数えに入れる前の時点で、すでに32倍のデータ増幅です。

さらにZFSは、書き込みをトランザクショングループ（TXG）にまとめ、およそ5秒ごとにフラッシュします。O_DIRECT を無視してすべてをARCにキャッシュし、その後、ディスクのmetaslabアロケータを介して大きなシーケンシャルバッチを書き出します。ZFSのパネルで書き込みが10GB全域に散らばって見えるのはこのためで、metaslabアロケータはウェアレベリングのために意図的に書き込みを分散させています。

recordsize=4k を設定すれば、このワークロードにおけるレコードレベルの増幅は解消されますが、シーケンシャルリードの性能は悪化します。これは混合ワークロードにおけるZFSの根本的なトレードオフです。

なぜBtrfsはここで効率的なのか

Btrfsはエクステントベースの割り当てを行います。4KBのCOW書き込みは、新しい場所に4KBのエクステントを1つ生み出します。1:1です。fallocate=none（事前割り当てなし）では、すべての書き込みが新規割り当てになり、ブロックアロケータはセクタを順番に払い出します。その結果、fioが論理的にはランダムな書き込みを発行しているにもかかわらず、write amplificationはほぼゼロで、物理I/Oパターンは完全にシーケンシャルになります。

fioの設定に関する注意：fioはデフォルトで、ランダムI/Oを開始する前にテストファイルを fallocate() またはシーケンシャル書き込みで事前確保します。Btrfsでは、この事前割り当てエクステントのせいで、以降のCOW書き込みが（元のエクステント位置の近くに着地するため）散らばって見えてしまいます。本実験ではこれを無効化し、本来のCOW割り当てパターンを観察するために --fallocate=none --create_on_open=1 を使用しています。

実験4：COWファイルシステムでのスナップショット

LVMと違い、ZFSとBtrfsはもともとCOWです。では、スナップショットを取ると何か変わるのでしょうか？

3つのフェーズ

  1. Phase 1（10秒）：新規ファイルへの初回書き込み
  2. Phase 2（30秒）：スナップショット#1の後 — 古いブロックはピン留めされ、再利用できない
  3. Phase 3（10秒）：スナップショット#2の後 — Phase 2の中間ブロックの一部が再利用可能に

フェーズをまたいでもI/Oスループットはほとんど変わりません。LVMのような37倍のスローダウンは起きないのです。しかしBtrfsでは、割り当てパターンが劇的に変化します：

PhaseBtrfsのシーケンシャル率説明
Phase 1100%新規ファイル、事前割り当てなし → アロケータがブロックを順番に割り当てる
Phase 2100%スナップショットが全ブロックをピン留め → 再利用不可 → 純粋なシーケンシャル割り当て
Phase 370%Phase 2の中間COWブロック（snap1にピン留めされていないもの）が再利用可能になる

Phase 3のBtrfsパネルをよく見てください。1本のシーケンシャルなラインではなく、書き込みがディスク上の複数のバンドに分かれています。アロケータは、部分的に解放された複数のブロックグループ（Phase 2の中間COWデータが解放された場所）から空きブロックを引き出しつつ、同時に上部でシーケンシャルな書き込みフロンティアを前進させています。これが、複数のスナップショットを抱えたCOWのフラグメンテーションの姿です。スループットには影響しませんが、物理レイアウトは散らばっていきます。

COWスナップショットの隠れたコスト：性能は落ちませんが、ディスク消費量が増え続けます。古いブロックを解放できないため、COW書き込みのたびに新しい領域を消費するのです。プール使用率96%のZFS + スナップショット = 書き込みが完全に停止します（ENOSPC）。「プールは80%未満に保て」というルールはこのために存在します。

再現方法

すべての実験は、10GBのvirtioディスク2台を備えたQEMU/KVM VMで実行しました。完全なセットアップはリポジトリにあります。

VMはQEMU/KVM上のUbuntu 24.04で、10GBのvirtioディスク2台、4 vCPU、4GB RAMという構成です。cloud-initで dev ユーザーをプロビジョニングし、build-essential、fio、blktrace、lvm2、zfsutils-linux、btrfs-progs をインストールします。

# Experiment scripts (run inside VM as root)
scripts/run_linear.sh       # LVM linear + snapshot
scripts/run_thin.sh         # LVM thin + snapshot
scripts/run_zfs.sh          # ZFS basic
scripts/run_btrfs.sh        # Btrfs basic (with --fallocate=none)
scripts/run_snap_long.sh    # ZFS/Btrfs with multiple snapshots

# All I/O captured with blktrace, parsed with blkparse,
# extracted to JSON with:
blkparse -i trace -q | awk '$6=="C" && $7~/[WR]/{
  printf "{\"t\":%.6f,\"s\":%d,\"n\":%d,\"type\":\"%s\"},\n", $4, $8, $10, $7
}'
